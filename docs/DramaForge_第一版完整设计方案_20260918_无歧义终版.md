# DramaForge 第一版完整设计方案（最终定稿版）

> 基线：以执行开始时重新确认的 `origin/dev` 准确提交为事实基线  
> 目标：不再为了版本号提前发布。把当前二维影视制作工作台做完整、做稳定后，再作为第一版发布。  
> 原则：先证明问题存在再改代码；正确性、安全性和闭环优先于结构美化。  
> 下一版再进入自由画布、三维场景、三维调度、虚拟机位、空间预演等导演台能力。

---

# 零、文档权威与判定规则

这两份方案的职责必须分开：

```text
设计方案
→ 定义第一版目标、事实源、产品语义、架构边界和不可违反的合同

执行方案
→ 定义阶段顺序、Owned Scope、测试、证据和发布 Gate
```

若两份文档出现冲突：

```text
产品 / 数据 / 运行时语义冲突
→ 以设计方案为准

执行顺序 / 测试 / 发布证据冲突
→ 以执行方案为准
```

仓库当前代码、数据库迁移、OpenAPI、运行证据用于说明“现在是什么”，不能因为和目标设计不同就被当成目标正确。仓库治理文件、受保护分支规则或强制合同若与方案冲突，必须先显式协调，禁止 Agent 静默绕过。

每个阶段状态只允许使用：

```text
已验证，无需修改
已确认问题，待修复
已修复并通过
非第一版阻塞项，延期
阻塞，未通过
```

禁止为了完成阶段而制造无必要代码变更。

## 持续 Goal 与有界 Task 的关系

“持续执行到 `RELEASE_DONE`”是**整个第一版 Goal 的编排规则**，不是允许单个 Task 无限扩张。

```text
第一版 Goal
→ 持续推进，不因任务长而人为停止

单个 Task
→ 必须有明确 Goal / Owned Scope / Risk / Tests / Acceptance
→ 只修改一个 bounded 问题
→ 完成后形成 review checkpoint
→ review 通过后由编排层立即进入下一 Task
```

因此不得把“持续执行”解释为一个 Agent 在同一工作区长期累积未审查的大 diff；也不得把“Task 已完成”解释为整个 Goal 可以停下。

以下内容属于**动态发布证据**，设计方案不硬编码具体值：

```text
执行时的 origin/dev SHA
正式支持的 Provider / Model 实际清单
仓库当前 required checks / 测试命令
是否支持某个 pre-release 数据库升级
正式 Compose 的宿主平台 / 架构 / 资源实测值
最终镜像 digest
```

这些必须在执行时从最新仓库和运行环境取得；证据缺失时标记阻塞或待验证，禁止用旧对话、旧文档或猜测补值。

# 一、语言与界面总原则

## 1. 用户界面必须使用中文创作语言

普通创作者界面不得直接出现**内部实现标识**：

```text
代码类名
数据库字段名
接口字段名
运行时对象名
供应商请求字段
哈希值
内部协议版本号
内部技术缩写
开发者术语
```

这不是“禁止英文”。模型名、供应商名、文件格式名和行业中本来就需要识别的专有名词可以保留，例如模型版本、MP4、SRT；关键是不能把内部 schema / runtime 字段当成产品语言。

例如以下内容不得直接出现在普通用户界面：

```text
NodeRun
ProviderOperation
Artifact
Proposal
Runtime
Skill
Style
Prompt
Binding
Manifest
contract_hash
reference_strength
execution_path_version
```

应转换为用户能直接理解的中文表达。

例如：

```text
NodeRun
→ 生成任务 / 执行任务

ProviderOperation
→ 模型执行记录

Artifact
→ 生成结果 / 媒体结果

Proposal
→ 导演建议 / 修改建议

Runtime
→ 执行系统

Skill
→ 创作技巧

Style
→ 画面风格

Prompt
→ 生成描述

Reference
→ 参考素材

Formal
→ 正式版本

Candidate
→ 候选结果
```

## 2. 技术标识只允许存在于内部

实际代码中的类名、文件名、接口路径、字段名可以保留真实标识。

但只能出现在：

```text
内部日志
开发者调试页
开发文档
错误追踪
接口文档
测试代码
```

不得直接暴露到普通创作者界面。

但产品透明性不能因此消失：用户可以看到自己选择的**供应商、模型、模型版本、支持能力、降级说明和结果来源**；只是不能直接操作供应商原始字段。开发 / 诊断详情可以进一步查看只读的运行、请求摘要和血缘证据。

## 3. 界面不得“专业化过度”

“专业”不等于把摄影、模型和后端术语堆给用户。

普通创作者界面优先表达：

```text
你正在制作什么
当前是什么镜头
现在用的是哪个正式版本
导演建议了什么
下一步可以做什么
结果为什么需要修改
```

而不是：

```text
技术参数
供应商能力表
模型原生字段
请求体
运行编号
哈希
节点状态机
接口状态码
```

## 4. 参数默认隐藏，按需要展开

第一层界面只展示创作语义。

例如用户看到：

```text
镜头景别：近景
镜头运动：缓慢推进
角色参考：已使用
画面风格：写实电影
人物动作：克制
```

而不是：

```text
camera_motion=push_in
reference_strength=0.82
motion_scale=0.65
seed=123456
```

确实需要高级控制时，放在：

```text
高级创作设置
```

中，并且仍然只表达创作语义。

另外保留独立的：

```text
开发 / 诊断详情
```

用于排障和验证，可只读查看真实运行编号、请求摘要、结果血缘、错误码等技术证据。它默认隐藏、明确标注为开发信息，不能变成普通创作者的参数面板。


## 5. 底层参数不得向用户界面泄漏

这是一条架构硬约束，不只是中文化要求。

正确分层：

```text
用户界面
→ 创作产品模型
→ 前端接口适配
→ 后端业务模型
→ 模型适配
→ 供应商具体请求
```

用户界面只能处理：

```text
镜头
角色
场景
动作
构图
画面风格
导演方式
创作技巧
参考素材
候选结果
正式版本
审查
修复
剪辑
下一步
```

以下内容只能存在于底层代码、接口适配、日志、调试或开发文档中：

```text
供应商原始字段
接口请求参数
数据库字段
内部任务编号
模型执行编号
内部状态机值
哈希
原始请求体
模型能力内部标识
内部版本号
供应商错误码
```

即使把这些参数翻译成中文，也不能直接变成普通用户界面。

错误示例：

```text
参考强度：0.82
任务状态：运行中
模型执行编号：xxxx
镜头运动参数：push_in
随机种子：123456
```

正确表达应是：

```text
已使用角色参考
正在生成
缓慢推进
保持角色外观
使用正式关键帧作为视频起始画面
```

## 6. 模型差异必须由底层消化

不同模型可能分别使用：

```text
reference_images
subject_reference
first_frame
reference_strength
camera_control
```

这些差异不能直接传到用户界面。

用户始终只操作统一创作概念：

```text
角色参考
场景参考
首帧
尾帧
镜头运动
角色连续性
参考程度
```

具体如何映射到不同模型，由模型适配层决定。

因此：

```text
同一个“角色参考”
→ 模型甲可能使用参考图
→ 模型乙可能使用主体参考
→ 模型丙可能只能使用首帧 + 生成描述
```

用户不需要知道底层字段名称。

## 7. 高级设置也必须保持创作语义

“高级设置”不能退化成供应商参数面板。

允许展示：

```text
更接近参考素材
更强调角色连续性
保持服装
镜头运动更明显
生成时长
画面比例
清晰度
是否使用首帧 / 尾帧
```

禁止直接展示：

```text
原始供应商字段
原始数值范围
原始请求 JSON
内部枚举值
内部能力键名
```

只有明确进入开发 / 诊断详情时才允许查看原始技术信息；这些信息只用于排障、验收和追踪，不参与普通创作交互。

## 8. 错误信息必须产品化

底层错误可以记录：

```text
供应商超时
任务状态错误
接口状态码
内部错误码
```

用户界面应转换为可行动的创作提示，例如：

```text
生成等待时间较长，可以继续等待或重新生成。
当前结果未生成成功，请检查参考素材后重试。
当前模型不支持这种参考方式，可改用首帧或更换模型。
```

不得把内部错误码直接弹给创作者。

# 二、第一版目标

DramaForge 第一版应当是一套：

```text
可本地部署
单用户稳定使用
以影视制作流程为中心
能够持续与导演助手协作
能够控制画面风格和创作方法
能够管理候选结果和正式版本
能够完成审查、修复、剪辑与最终导出
```

的二维导演工作台。

完整流程：

```text
项目
→ 故事 / 剧本
→ 角色与场景素材
→ 场次 / 镜头
→ 创作类型 / 画面风格 / 导演方式 / 创作技巧
→ 导演规划 / 手动镜头设计
→ 有效创作意图
→ 执行计划
→ 生成任务
→ 模型执行
→ 生成结果
→ 候选结果
→ 精确审查
→ 正式版本
→ 修复
→ 剪辑
→ 成片
→ 视频 + 字幕
```

第一版完成不是“页面能点通”，而是：

```text
用户操作
→ 前端行为
→ 唯一后端写入口
→ 数据库正式事实
→ 执行系统
→ 模型生成
→ 结果落库
→ 页面重新读取
→ 刷新后仍然一致
```

整条链全部成立。

## 第一版必须冻结有限发布面

第一版不能用“理论上支持”定义范围。进入正式发布验证前必须形成两个 Manifest：

```text
FirstReleaseModelManifest
→ 正式支持的供应商
→ 正式支持的模型 / 版本
→ image / video / reference / first-frame / last-frame 等能力
→ 哪些能力只做合同验证
→ 哪些 Provider 需要真实 smoke / golden

FirstReleasePlatformManifest
→ 正式支持的宿主平台 / CPU 架构
→ Docker / Compose 最低要求
→ 默认端口与外部网络依赖
→ 持久化卷与最低磁盘要求
→ 已验证的单用户资源基线

FirstReleaseCreativeCapabilityManifest
→ 正式发布的创作类型
→ 画面风格
→ 导演方式
→ 创作技巧
→ 每项声明的 effect / 适用阶段
→ 每项的版本、来源和 E2E 状态
```

Manifest 之外的能力不得在第一版 UI 中伪装成“正式支持”。**默认普通产品面不展示未验证 / 实验能力**；若仓库必须保留实验入口，只能放在明确的开发 / 实验开关之后，默认关闭，并明确标成实验性且不计入第一版支持承诺。外部来源审查的目标是补齐 Manifest 所需能力，不是无限吸收仓库。

Manifest 采用“最小代表集”原则：先保证少量风格 / 导演方式 / 创作技巧完整走通真实 effect chain，再扩数量；当前 Manifest 中任一能力尚未 E2E 闭环时，不继续为了数量新增同类能力。

`FirstReleaseModelManifest` 中每个正式模型还必须声明验证级别，避免“每个模型都跑昂贵 Golden”和“只测一个模型却宣称全部支持”两个极端：

```text
contract
→ deterministic fixture / captured request / capability mapping 必须通过

real_smoke
→ 该 Provider / transport 的真实 submit / poll / result 至少有一次有效证据

release_golden
→ 被选为最终发布代表路径，进入完整真实媒体与 Computer Use 创作
```

所有正式模型至少满足 `contract`；每种第一版正式 Provider / 独立 transport 至少有足够的 `real_smoke` 证明真实 wire；最终图片 / 视频主路径至少各有一个 `release_golden`。若某模型具有不能被同 Provider 其他模型覆盖的独特真实 wire 或能力，则必须提高其验证级别。

# 四、核心事实边界

## 1. 一个概念只能有一个正式事实源

必须保持：

```text
镜头正式内容
→ 镜头域拥有

正式图片 / 正式视频
→ 服务端正式版本绑定拥有

生成执行状态
→ 执行任务 / 模型执行记录拥有

导演对话
→ 导演会话与消息拥有

导演修改建议
→ 导演建议与用户决定拥有

创作能力配置
→ 已冻结的有效创作意图拥有

审查结果
→ 指向具体媒体结果的审查记录拥有
```

禁止：

```text
旧接口写一份
新接口又写一份
前端本地状态再保存一份
```

## 2. 素材与版本最小合同

第一版完整流程包含素材，因此素材不能只是“有个上传入口”。至少保证：

```text
素材按项目隔离
引用固定到明确素材版本
上传 / 导入 / 生成结果采用都能形成可追踪来源
正式引用不能被后续同名素材静默替换
删除 / 归档不能破坏已有 Artifact lineage
用户选择生成结果加入素材时必须显式发生
```

第一版不要求复杂 DAM / 审批系统，但不能用可变 URL 或“最新素材”代替明确版本身份。

已经被 Shot、ExecutionPlan、Artifact lineage 或 Final Assembly 引用的素材版本视为**不可变历史事实**：普通“删除”只能归档 / tombstone 或拒绝删除，不能物理移除导致旧结果失去来源；要替换只能创建新版本并显式重新绑定。

# 五、导演系统与生产执行系统必须分离

## 1. 导演系统负责

```text
持续对话
读取上下文
理解用户意图
推荐创作技巧
给出导演建议
生成修改建议
等待用户决定
在授权后发起生产执行
```

## 2. 生产执行系统负责

```text
生成任务
排队
工作进程执行
模型调用
状态恢复
结果落库
失败重试
中断恢复
```

## 3. 导演写入必须区分“事实修改”和“生产执行”

导演讨论永远是只读。导演提出修改以后，先形成可审查的建议，再根据建议类型进入不同正式入口：

```text
A. 事实修改建议
导演助手
→ 修改建议
→ 用户接受 / 已有明确预授权
→ 对应领域的版本化正式写入口
→ 更新镜头 / 场次 / 项目等 canonical fact
→ 不因为修改事实就自动创建生成任务

B. 生产执行建议
导演助手
→ 执行建议
→ 用户接受 / 已有明确预授权
→ Typed Production Command
→ Production Runtime
→ NodeRun / ProviderOperation / Artifact
```

因此“接受导演建议”不等于“所有修改都必须经过 Production Runtime”。只有真正需要生成 / 重生成 / 渲染的动作才委托 Production Runtime。

导演助手不得：

```text
直接调用模型
偷偷修改镜头
偷偷切换模型
偷偷重试
偷偷改变生成描述
```

## 4. 三种创作模式共享同一条生产链

```text
自动
辅助
手动
```

三种模式只改变“谁提出决定、何时需要确认”，不改变正式事实源、执行系统和结果模型。

自动模式必须由用户先设定可持久化、可撤销、可查看的授权范围，例如：

```text
允许自动推进哪些阶段
允许使用哪些模型 / 供应商
允许自动重试几次
是否允许自动采用通过既定规则的候选
哪些动作必须停下来确认
```

```text
自动 ≠ 无限授权
```

正式版本替换、模型切换等高影响动作可以被**明确预授权**，但绝不能静默发生。超出预授权范围、改变用户硬约束、需要扩大修改范围或发生未声明降级时，必须暂停并请求用户决定。

创作模式本身是项目级默认策略，可以在项目内切换；切换只影响后续决策，不复制项目、不建立第二套 Scene / Shot / Runtime，也不重写已经存在的 Formal / Artifact。场次或镜头若需要不同确认策略，应作为局部 policy override，而不是另起工作流。

第一版 AUTO 的含义是“在授权范围内自动规划 / 生成 / 恢复并在明确 checkpoint 停下”，不是为了追求无人值守而新造自动审片 Runtime。候选仍进入同一 Exact Review checkpoint；已有审查决定后，可以按用户预授权规则自动采用 Formal。完全无人值守的视觉质量判定不在第一版新增范围。

### 自动授权策略必须是可版本化的正式事实

任何“命中预授权”都不能只靠内存布尔值或一句 `AUTO=true`。至少要能确定：

```text
policy identity / revision
作用范围：项目 / 场次 / 镜头
允许的 action 集合
允许的 Provider / Model 范围
自动 retry 上限
Formal 自动采用条件
硬约束 / 禁止动作
有效期 / 撤销状态
```

每次自动动作必须记录“命中了哪一版 policy、针对哪个目标、执行了什么决定”。已撤销、过期或 scope 不匹配的 policy 不能授权新动作；policy 修改只影响后续动作，不追溯改写已经完成的生产事实。

# 六、创作能力系统

## 1. 创作能力不是关键词库

画面风格和创作技巧必须真正影响：



# 十、有效创作意图

所有创作配置最终编译成统一的：

```text
有效创作意图
```

至少包含：

```text
故事意图
画面意图
镜头意图
表演意图
连续性要求
参考素材策略
生成描述指导
生成限制
质量要求
修复指导
来源记录
```

生效规则不使用“导演建议”作为独立于范围之外的一层优先级。

先按作用范围解析，但必须采用**按维度 / 字段合并**，不能用“整个镜头对象覆盖整个场次对象”的粗暴替换：

```text
镜头级字段
>
场次级同字段
>
项目级同字段
>
模板 / 默认值
```

例如镜头级只改“景别”，不得顺带抹掉项目级画面风格；显式清空必须使用明确的 unset / inherit 语义。

用户接受导演建议以后，建议必须物化成目标范围内的正式覆盖，并保留来源：

```text
镜头级覆盖（来源：已接受导演建议）
场次级覆盖（来源：已接受导演建议）
项目级覆盖（来源：已接受导演建议）
```

同一范围、同一字段内不能再用“用户手动 > 已接受导演建议”这种固定来源优先级。**一旦用户接受导演建议，它就是新的 canonical explicit decision。**

```text
最新有效 explicit revision
（来源可以是用户直接编辑，也可以是用户接受的导演建议）
>
尚未接受的系统推荐 / 模板
>
默认值
```

`source=用户直接编辑 / 已接受导演建议`只负责 provenance，不负责把旧值永久压在新决定之上。若用户先手动设为近景、后来接受“改成中景”，新的已接受 revision 必须生效；如果之后用户再手动改回近景，则更晚的 explicit revision 再次生效。所有 apply 都继续受 stale / base revision gate 约束。

## 执行时必须冻结快照

当一次生成进入正式执行计划时，必须冻结该次执行真正使用的创作事实：

```text
有效创作意图快照
风格 / 导演方式 / 创作技巧版本
参考素材版本
Compiler 版本
模型能力 Manifest 版本
模型 / 供应商绑定
授权 / 降级决定
```

后续用户修改项目风格、技巧或模型配置，只影响新的执行；不得反向改变已经创建的 NodeRun / Artifact 的解释。Artifact 必须能追溯到这一冻结快照。

角色连续性不能只依赖文字，也不能把“使用参考素材”描述成保证绝不漂移。第一版提供的是**角色参考与连续性控制**。

优先使用可验证的硬控制与正式素材，典型顺序：

```text
角色正式素材
>
正式素材版本
>
身份参考图
>
服装参考图
>
面部参考图
>
全身参考图
>
首帧 / 尾帧
>
模型原生参考能力
>
结构化生成描述
>
普通文字约束
```

系统内部根据具体模型能力决定如何使用：

```text
参考图
主体参考
首帧
尾帧
参考强度
镜头运动控制
文字约束
```

用户界面只显示：

```text
角色参考：已使用
服装参考：已锁定
首帧：使用正式关键帧
连续性：已启用
```

不得直接显示模型字段名。

# 十三、模型适配

内部正式链：

```text
模型目录
→ 模型绑定
→ 模型适配
→ 请求编译
→ 执行
→ 网络调用
→ 模型结果
```

普通创作流程不需要看到这条技术链，但用户必须知道自己实际选择了哪个供应商 / 模型，以及某项创作要求是否被模型完整支持。

用户看到：

```text
供应商 / 模型 / 模型版本
可用创作能力
当前请求是否发生能力降级
生成中 / 已完成 / 生成失败
需要重新生成
```

任何能力降级都必须明确记录：

```text
缺少什么能力
采用了什么替代
会影响什么结果
是否需要用户确认
```

不得静默删除用户意图。

## 模型连接与配置也是第一版正式能力

生成链能否使用取决于连接、凭据和模型绑定，因此第一版必须有明确配置闭环：

```text
配置供应商连接
→ 服务端安全保存凭据
→ 测试连接 / 鉴权
→ 读取或配置可用模型
→ 建立 DramaForge 模型绑定
→ 校验能力声明
→ 项目 / 镜头选择模型
```

普通创作界面可以选择供应商 / 模型，但不能编辑原始 API payload。密钥不得返回前端明文、不得写入日志、不得进入 Artifact lineage、Release Manifest 或离线包。

连接失效、模型不可用、能力不匹配必须形成可行动错误，不能在生成时才以原始供应商错误码爆出。

# 十四、候选结果与精确审查

## 1. 核心原则

任何审查必须围绕：

```text
具体媒体结果
```

而不是猜：

```text
最新结果
当前正式版本
最近一次生成
```

## 2. 普通候选

```text
候选结果甲
→ 审查甲
→ 批注甲
→ 决定甲
→ 用户设为正式版本
```

## 3. 修复候选

```text
正式版本甲
→ 修复
→ 候选结果乙
→ 审查乙
```

必须保证：

```text
播放器 = 乙
审查依据 = 乙
批注 = 乙
决定 = 乙
```

甲的迟到请求不能覆盖乙。

## 4. 审查与正式版本的关系

第一版正式流程要求：

```text
候选结果
→ 精确审查
→ 审查决定
→ 设为正式版本
```

```text
审查通过
≠
自动设为正式版本
```

设为正式版本必须来自用户显式操作或用户事先配置的明确自动授权规则；无授权时不得跳过审查、不得自动 Formal。

自动 Formal 只有同时满足以下条件才合法：

```text
审查决定精确绑定当前 artifact
审查决定属于可采用 / approve 状态
审查事实未 stale
候选仍属于当前 project / shot / stage
当前授权 policy revision 明确允许该 action
Formal 写入通过版本 / stale gate
```

Reject、Needs Repair、目标不匹配、迟到审查结果或已撤销 policy 都不能触发自动 Formal。自动采用也必须留下 `actor=policy` / policy revision 等可审计来源。

所有可能覆盖用户当前决定的写入（Formal、导演建议应用、EditSession 等）必须带版本 / stale gate；迟到响应只能被拒绝或重新读取，不能静默覆盖更新状态。

# 十五、执行模块边界

现有执行模块继续收口，但不为了拆文件而拆文件。

核心目标：

```text
重试规则
取消规则
恢复规则
模型请求
生成描述
结果血缘
数据库结构
接口语义
```


# 十八、物理目录整理

目录整理是**条件性结构治理**，不是天然的第一版发布硬门槛。

只有当前目录已经导致以下真实风险时才在第一版迁移：

```text
双写入口
双执行路径
错误依赖方向
职责 owner 无法证明唯一
安全 / 权限 / Provider authority 无法证明
阶段 1～3 因目录结构无法完成收口
```

如果只是命名或层级不够理想，则记录到下一阶段清理，不为了“漂亮”制造大规模 import churn。

若必须迁移，目标是让开发者能从目录看出：

```text
访问控制
素材
导演
剪辑
执行
生产
模型供应商
审查
交付
维护
公共能力
```

迁移只允许 move / rename / import rewrite / export cleanup，且不得顺便：

```text
改业务
改接口
改数据库
改状态机
改模型请求
加新功能
```

# 十九、导演持续制作对话

## 1. 目标

导演助手不再只是固定按钮式建议，而是可以长期围绕同一作品讨论、提出修改建议并在授权后委托执行。它不是无限制通用聊天代理。

例如：

```text
“这场戏为什么太平？”
“女主很生气，但不要直接表现出来。”
“第二个镜头改，第一个别动。”
“这个镜头还能怎么拍？”
“按现在这个风格继续。”
```

## 2. 三类对话

### 讨论

```text
用户提问
→ 导演解释
→ 不修改任何生产内容
```

### 修改建议

```text
用户要求修改
→ 导演解释
→ 给出修改建议
→ 用户接受 / 拒绝 / 修改
```

接受前不得写入正式生产内容。

### 执行请求

```text
用户要求重新生成
→ 导演说明将要执行什么
→ 等待用户授权
→ 生产执行系统执行
```

## 3. 导演可以读取

```text
项目
场次
镜头
正式素材
参考素材
当前风格
当前创作技巧
当前生产状态
审查结果
已接受决定
对话摘要
```

生产事实每个 Turn 都必须从 canonical read model 读取；对话摘要只压缩历史讨论，**不能代替当前生产事实**。

导演上下文必须有预算：优先当前项目 / 场次 / 镜头 / Formal / 待处理决定，较旧对话进入摘要或按需检索，禁止无限拼接全部历史。只读工具必须是 typed、可审计的，不允许通过“通用工具”绕过领域边界。

## 4. 导演不得拥有

```text
生成任务
模型执行记录
正式媒体事实
供应商密钥
模型调用权限
```

# 二十、当前二维工作台最终形态

第一版继续使用二维制作工作台。

核心流程：

```text
镜头设计
→ 生成
→ 候选结果
→ 精确审查
→ 正式版本
→ 导演
→ 修复
→ 剪辑
→ 成片
```

## 1. 主界面视觉重心

始终优先：

```text
当前镜头
画面
正式版本
当前决定
下一步
```

## 2. 技术信息下沉

普通用户不直接看到：

```text
运行编号
模型执行编号
请求字段
哈希
原始数据
接口字段
```

只看到产品化后的事实：

```text
供应商 / 当前模型 / 模型版本
当前状态
结果版本
结果来源
是否发生能力降级
可理解的失败原因
```

原始 request、运行编号和 provider-native 字段仍只在开发 / 诊断详情中只读查看。

## 3. 一个区域一个主操作

候选结果的“当前预览”只属于界面临时选择，不得改变服务端 Formal truth。刷新后以服务端 Formal 为准。

候选结果区域的主操作随状态变化：

```text
未审查候选
Primary = 审查候选

已审查、可采用
Primary = 设为正式版本

已正式
Primary = 下一步 / 导演 / 修复（按当前阶段）
```

次操作可以是重新生成、比较、查看详情，但不能绕过“候选 → 精确审查 → Formal”的正式流程。

不要同时出现大量：

```text
保存
确认
提交
应用
继续
完成
```

造成语义重复。

产品 Gate 应尽量转成可自动断言：当前镜头标识、Formal 标识和 next action 在主工作区可定位；普通页面不存在 raw provider / runtime 字段；候选与 Formal 使用不同状态标签；同一状态只存在一个 primary action。主观“看起来更专业”不能单独作为验收依据。

# 二十二、剪辑与最终成片

正式流程：

```text
每个镜头正式版本
→ 剪辑时间线
→ 成片合成
→ 视频文件
→ 字幕文件
```

必须保证：

```text
不会使用未确认候选结果
不会使用旧修复结果
不会因为刷新回滚
不会被旧编辑会话覆盖
```

第一版不做完整专业剪辑软件，也不新造第二套时间线 truth。若现有编辑器 / OpenCut 集成继续使用，它只能消费同一套服务端 Formal Shot source，并通过版本化 EditSession 写入编辑事实。

第一版至少需要：

```text
镜头顺序
基础裁切 / 时长
基础字幕
基础音频
最终成片
```

最终导出必须从同一条正式 Timeline / EditSession 事实链产生，不允许“预览一套、导出另一套”。验收不仅看文件存在，还要验证视频可解码、时长 / 镜头顺序合理，字幕时间戳合法且与时间线对应。

开始一次 Final Film 导出时必须冻结**成片装配快照**（可以复用现有版本化事实，不要求一定新增表）：

```text
Timeline / EditSession revision
精确 Shot 顺序与时长
每个 Shot 使用的 Formal artifact/version
字幕 / 音频引用版本
导出参数版本
```

导出进行中即使用户后来更换某个 Formal，也不能静默改变正在执行的这次成片；需要新内容时创建新的导出 / 装配快照。

# 二十三、创作能力验证分为“合同正确性”和“媒体质量”

第一版必须区分两类证据。

## 1. 系统合同正确性：发布硬门槛

必须确定性证明：

```text
风格 / 技巧选择
→ 有效创作意图发生预期变化
→ 镜头设计 / 参考策略发生预期变化
→ 图片 / 视频生成描述正确编译
→ 模型适配只使用模型支持的能力
→ 实际请求与能力声明一致
→ 结果血缘可追踪
```

这些可以通过结构、fixture、请求捕获和真实调用证据判断。

## 2. 真实媒体质量：质量证据

真实生成时使用固定的最小代表场景集观察：

```text
角色参考与连续性控制
画面风格
对白覆盖 / 轴线
情绪表演
镜头运动
```

每个对外宣称支持的核心能力至少要有一条真实媒体证据；这不是统计学质量承诺，而是发布前 sanity evidence。

生成模型具有概率性。单次结果没有完全遵从，不自动等于系统合同失败。

但如果出现系统性偏离，则必须回查参考策略、生成描述、模型能力映射或模型选择。

因此 DramaForge 第一版承诺的是：

> 把用户意图和可用控制正确、透明、可追踪地送入模型，并提供审查 / 修复闭环；不承诺闭源生成模型每次都百分之百服从。

# 二十四-A、测试与真实用户验收分层

第一版不采用“每写完一点就跑完整全流程”的开发方式。

验证分四层：

```text
第 1 层：局部改动
→ 最小相关单测 / 类型检查 / 静态检查

第 2 层：阶段收口
→ 相关集成测试 / 合同测试 / 局部 8080 路径

第 3 层：发布候选 RC
→ 完整 CI / 8080 / Recovery / Golden / 安装验证

第 4 层：GPT + Computer Use
→ 像真实用户一样通过 8080 从首次启动完成到最终成片
```

验证范围由改动影响面决定，而不是由“是否刚提交代码”决定。

小改动不反复烧完整环境；只有无法证明影响边界、改动跨越事实源，或进入最终发布候选时，才扩大为完整回归。

## GPT + Computer Use 的定位

Playwright、API 测试和合同测试证明机器可断言的正确性；Computer Use 负责发现这些测试很难覆盖的真实使用问题：

```text
用户是否知道下一步
操作是否重复 / 歧义
状态是否让人理解
Candidate / Formal 是否混淆
Director 聊天 / 建议 / 授权是否混淆
等待和错误反馈是否可理解
刷新 / 返回 / 重进是否自然
有没有真实 UI 死路
最终是否真的能完成作品
```

Computer Use 必须使用正式 `8080` 产品入口，只走普通用户可见 UI，不允许用内部 API、数据库写入、开发服务器或人工状态修正绕过产品缺陷。

Computer Use 发现的问题先分类，避免把所有视觉偏好都升级成发布阻塞，也避免把真实 UX 死路降级成“体验建议”：

```text
正确性 / 数据 / 状态 bug            → 第一版必须修
核心创作流程阻断                    → 第一版必须修
会让正常用户无法判断下一步的核心歧义 → 第一版必须修
安全 / 凭据泄漏                     → 第一版必须修
外部 Provider 暂时失败               → 按恢复合同处理，不伪装成产品 bug
纯装饰 / 非核心体验建议              → 可记录 backlog，不阻塞发布
```

允许进入 Known Limitations 的问题不得涉及数据错误、silent overwrite、权限 / secret、安全、核心流程死路、错误 Formal / Artifact 或无法完成成片。

发现需要修复的问题后采用：

```text
发现问题
→ 保存复现证据
→ 修复代码
→ 增加对应测试
→ 跑最小相关回归
→ 重跑受影响 UI 路径
→ 继续创作
```

不要求每个小修复后都从零重新跑完整作品。只有当改动影响前序事实源、迁移、权限、正式版本、Director 授权 / 恢复、Production Runtime、Provider request / polling / idempotency，或影响范围无法可靠界定时，才扩大回归范围。

最终发布候选必须额外满足一次全新环境完整通过：

```text
GPT + Computer Use
→ 首次启动
→ 配置模型
→ 创建项目
→ 故事 / 剧本 / 素材
→ 场次 / 镜头
→ Director 对话与决策
→ 关键帧生成 / 审查 / 正式版本
→ 视频生成 / 审查 / 正式版本
→ 修复
→ 剪辑
→ 成片
→ 导出视频 + 字幕
```

这一最终轮必须是零代码修改、零数据库手工修正、零内部 API 绕过、零人工替代关键操作。

# 二十四-B、持续执行与模型资源授权

## 1. 第一版采用持续执行目标，而不是短任务停顿式开发

执行代理的目标不是“完成一个 Task 就停”，而是持续推进第一版主线：

```text
证据确认
→ 实现 / 修复
→ 最小相关验证
→ 阶段闭环
→ 下一阶段
→ 发布候选
→ 最终发布
```

只要仍存在可执行的第一版任务，就不应因为调用次数、执行时间、任务长度或已经完成若干阶段而自行结束。

默认终态只有：

```text
RELEASE_DONE
```

或存在真实不可自行解除阻塞时：

```text
GOAL_BLOCKED
```

## 2. DeepSeek + Agnes 第一版持续授权

Owner 对第一版范围内使用 DeepSeek + Agnes 提供持续授权：

```text
不设置人为调用次数上限
不设置人为阶段上限
无需每次调用重新确认
可以用于开发、调试、真实生成、修复验证、Computer Use 创作和最终 Golden
```

这项授权解决的是“不要因为调用多就停止推进”的执行问题，不改变真实供应商的配额、余额、限流和服务约束。

如果真实账户 / 配额不可用，应作为外部阻塞记录，不得伪造模型成功，也不得静默切换成未授权模型。

## 3. 持续授权不改变模型能力与架构边界

DeepSeek / Agnes 必须继续经过既有正式能力和执行边界：

```text
FirstReleaseModelManifest
→ Model Binding
→ Capability Validation
→ Canonical Intent
→ Provider / Model Adapter
→ Production Runtime
```

Director 与 Production Runtime 仍然分离；模型持续可用不意味着 Director 可以直接拥有生成任务或 Provider 调用。

同样：

```text
不支持的能力必须明确失败或显式降级
不得 silent model switch
不得跳过用户授权边界
不得跳过 Review / Formal
不得用模型结果覆盖 canonical production truth
```

## 4. “持续使用”与“分层测试”同时成立

第一版明确不采用两种极端：

```text
极端 A：为了省调用，缺少真实模型证据也停止
极端 B：每改一点都重新跑完整作品并重复付费生成
```

正确策略是：

```text
模型资源不设人为调用上限
+
验证范围按改动影响面选择
+
需要真实模型才能判断时就真实调用
+
没有新增证据价值时不机械重复调用
```

因此，“持续执行直到第一版完成”和“不要每写完一点就全量测试”是同一执行策略的两面，而不是矛盾规则。

## 5. 允许整体停下的条件

只有真实外部硬阻塞才允许停止第一版主线，例如：

```text
必要 Provider / DeepSeek / Agnes 凭据或配额不可用
必要外部服务不可用
需要 Owner-only 权限动作且执行主体无权限
环境缺少无法自行恢复的基础能力
出现必须改变第一版产品边界的决策冲突
```

局部阻塞不应自动等于整个 Goal 停止；如果仍存在同阶段可安全完成且不引入 authority 冲突的任务，应继续推进。

# 二十四、稳定性与恢复

第一版发布前必须验证：

```text
刷新页面
重启接口服务
重启全部容器
重启生产工作进程
重启导演工作进程
重复点击生成
网络中断后恢复
过期修改建议
过期编辑会话
模型轮询中断恢复
模型提交结果未知时恢复
失败任务重新执行
```

不得出现：

```text
同一幂等请求被重复提交到模型
状态丢失
正式版本回滚
旧候选覆盖新候选
假完成
孤立结果
静默覆盖
```

用户明确点击“重新生成”属于新的生产意图，应产生新的请求身份；不能因为有幂等保护而错误吞掉合法重生成。

第一版必须明确区分四种身份语义：

```text
resume / poll continuation
→ 同一次生产意图、同一远端 operation，继续恢复

technical retry
→ 同一次用户生产意图下的新 attempt；必须继承幂等 / 去重约束

unknown submission recovery
→ 先通过已保存 operation id / provider idempotency key / query 能力对账
→ 不能在“不知道上次是否已提交成功”时盲目再次 submit

user regenerate / repair regenerate
→ 新的生产意图 / 新请求身份，并明确 lineage 指向上一结果或 RepairStep
```

如果 Provider 无法安全对账 unknown submission，且再次提交可能产生重复付费或双结果，状态必须进入可解释的待处理 / 阻塞分支，不能用“自动 retry”掩盖不确定性。

发布诊断还必须满足：

```text
失败的生成 / Director turn 能通过只读诊断信息关联到对应运行事实
日志足以定位失败阶段
凭据、Authorization header、完整 secret 不进入日志
Compose Restart 后持久化数据仍存在
```

第一版要求可靠持久化，不把完整备份 / 灾备系统扩进首版；数据卷位置与备份建议写入安装文档即可。

# 二十六、发布候选与验证证据模型

正式发布不允许“CI 验证一个版本、真实模型验证另一个版本、最后发布第三个版本”。

每个发布候选必须绑定：

```text
候选编号
验证源提交版本
Git tree / 运行内容身份
数据库迁移头
前端 / 后端 / Worker 镜像摘要
Compose / 配置模板版本
自动测试证据
8080 全流程证据
GPT + Computer Use 完整用户旅程证据
异常恢复证据
真实模型证据
在线安装证据
离线镜像包安装证据
```

证据中只能记录配置模板与必要版本信息，不得把真实密钥 / token 打进 release manifest、日志或离线包。

如果代码、依赖、迁移、镜像内容、生产配置或模型适配发生变化，产生新的发布候选，旧候选证据不能直接继承。

只有能证明不影响运行结果的纯文档修订，才允许保留已有运行证据，并明确记录“最终发布提交 ↔ 已验证运行候选”的关系。

所谓“离线镜像包安装”只表示安装时不需要在线拉取 / 构建镜像；如果选择云端模型，实际生成仍需要网络。

第一版必须保证 fresh install。对第一版之前的开发 / 测试数据库是否支持原地升级，必须在 Release Manifest 明确声明；没有被声明支持的 pre-release 数据不为了“兼容所有历史”建立永久迁移旁路。

正式 Compose 默认只暴露产品入口（目标为 `8080`）；数据库、缓存、对象存储等内部服务除非诊断需要，不作为默认宿主公开端口。安装文档必须根据实际测量声明首版支持平台、CPU 架构、Docker / Compose 前提、持久化位置以及单用户最低 / 推荐资源，而不是凭经验猜数字。

## 合并 main 后的身份规则

合并 `main` 可能产生新的 Git commit（例如 merge / squash 元数据），因此发布证据不能只比较 commit SHA。

```text
如果 main 合并后运行相关文件内容与已验证候选完全一致
→ 允许继承运行证据
→ 记录 validated_source_commit 与 main_release_commit 的映射

如果运行相关文件、依赖、构建输入或镜像发生任何变化
→ 建立新候选
→ 重新执行受影响 Gate；无法证明影响边界时重跑完整发布 Gate
```

Release tag 必须指向最终 `main` 发布提交；Release Manifest 同时记录已验证源提交、main 发布提交和最终镜像摘要。

若 main 合并只改变 Git 提交身份而运行内容完全相同，优先直接发布已经验证过的候选镜像，不为了让镜像标签里的 commit 变好看而无意义重建；一旦重建导致 digest 改变，就必须按新发行物重新证明等价或重新验证。

# 二十九、最终产品原则

第一版最终只坚持几件事：

> 用户看到的是创作，不是后端。  
> 用户操作的是镜头、素材、风格、导演建议和结果，不是模型参数。  
> 底层负责参数，界面负责创作；接口、数据库、运行时以及供应商原始参数差异不得向普通用户界面泄漏；供应商 / 模型身份与真实能力支持情况仍应透明。  
> 一个概念只有一个正式事实源。  
> 创作能力必须真正改变制作，而不是堆关键词。  
> 导演助手可以持续讨论和提出建议，但不能绕过用户决定或已授权边界。  
> 审查必须精确对应具体媒体结果。  
> 所有状态都必须可恢复、可追踪、可解释。  
> DeepSeek + Agnes 在第一版范围内持续授权，不因人为调用次数、任务长度或阶段数量停止推进；需要真实模型证据时持续调用，但不机械重复无新增证据价值的全量测试。  
> 第一版执行默认持续到 `RELEASE_DONE`，只有无法自行解除的真实外部硬阻塞才进入 `GOAL_BLOCKED`。  
> 当前二维工作台稳定以后再发布第一版。  
> 三维导演台和自由画布属于下一版。
