# DramaForge 模型能力插件化与视频生成抽象设计

> 状态：SUPPORTING / Provider 与模型执行层详细设计来源；只有当前任务涉及该层时读取
>
> 日期：2026-08-10
>
> 范围：Provider、模型目录、模型绑定、图像/视频生成、Agent Runtime、快速试制与专业模式

## 1. 结论先行

### 1.1 当前实现是否合格

当前实现**部分合格，但还不能称为完整的模型能力插件化**。

已经合格的部分：

- 已有 `ProviderPlugin` 注册表。连接创建、凭据保存、探测和模型绑定不再完全写死在 Agnes 分支中。
- 已有 `provider_type + protocol_profile` 组合，能够区分同一供应商的不同 Wire Contract。
- 已有 `documented -> contract_tested -> account_verified -> quality_gated` 四层证据状态。
- 已有 Agnes 与火山 Ark 两个真实协议客户端，覆盖请求、轮询、取消、错误归一化、请求脱敏和结果下载边界。
- 已经保留供应商差异：Seedance 的 `content[]`、MiniMax H3 的多模态角色、各家的任务查询方式，都不应被硬塞进同一份供应商 JSON。

还不合格的部分：

- 正式媒体执行仍在 `backend/app/execution/product_path.py` 中通过 `Flux/Agnes/Kling` 选择 Adapter，尚未按照项目的 `ProjectProviderBinding -> ProviderModelBinding -> Plugin` 解析。
- `ProviderPlugin` 目前主要描述连接和探测信息，不是完整的模型能力插件契约。
- 模型仍是每个用途一个固定 `model_contracts` 映射，不是可查询、可筛选、可版本化、可快照的模型目录。
- `video.generate` 还没有稳定的领域请求模型；Adapter 收到的是 `dict[str, Any]`，参数校验和能力协商无法做到类型化、可审计。
- 轮询恢复仍存在 Agnes 特判，例如 `product_path.py` 中的 `op.actual_provider == "agnes"` 和 `poll_persisted` 分支。
- 火山 Ark 已接入 Seedream/Seedance 的基础合同，但当前模型 ID、视频参数和模型可用性仍偏配置固定，不能支撑“一个账号多个 Seedance 模型”的选择。

结论：当前代码适合作为 P0/P1 的**供应商连接插件底座**，但不能继续让新目录与
Agnes 专用执行路径长期并存。当前实施范围确定为**阶段 A+B**：同时建立模型能力目录，
并把 Agnes、Ark 迁入 Binding 驱动的统一执行链。阶段 A 可以作为内部迁移检查点，但
不能单独作为本轮架构交付结果。

### 1.2 核心原则

不能把不同模型强行压扁成相同参数，也不能把供应商 JSON 暴露给产品层。

正确做法是三层分离：

```text
创作意图层
  用户/Agent 表达想拍什么、必须保留什么、可以偏好什么
  例如：首帧、尾帧、角色参考、时长、竖屏、需要原声

模型能力层
  声明某个模型真正支持什么、限制什么、哪些组合互斥、成本和证据状态
  例如：Seedance 支持 first_frame；H3 支持 first_frame + last_frame，
  但首尾帧模式与多模态参考模式互斥

协议编译层
  根据选中的模型，把已验证的创作意图编译成供应商 Wire Contract
  例如：Seedance 编译为 /contents/generations/tasks 的 content[]；
  H3 编译为 /v2/video_generation 的 content[]
```

`video.generate` 的价值是统一前两层的业务语义、生命周期和审计，不是规定所有供应商必须接收一份相同 JSON。

## 2. 要解决的真实问题

以用户配置火山方舟为例，一个连接下可能有多个 Seedance 模型。用户需要看到：

1. 当前账号可用哪些模型。
2. 每个模型能做哪些工作，例如文生视频、首帧图生视频、首尾帧、参考图、参考视频、参考音频、原声、草稿、固定种子。
3. 某个项目或某一个 Shot 的要求，哪些模型能满足，哪些不能满足。
4. 选中模型后，产品怎样不丢失该模型特有能力。
5. 模型更新、下线、换 Key、换地区、换 Host 后，旧项目怎样可复现、可解释、可恢复。

MiniMax H3 与 Seedance 的参数不相同并不是例外，而是常态：

- 有的模型要求一张 `first_frame`。
- 有的模型支持 `first_frame + last_frame`。
- 有的模型支持 `reference_image/reference_video/reference_audio`，但这些参考模式可能不能和首尾帧模式共用。
- 有的模型通过顶层 `duration`、`ratio`、`resolution` 控制输出；有的模型字段名和枚举完全不同。
- 有的模型是同步图片结果，有的是异步任务；有的返回 `task_id`，有的返回 `video_id + task_id`。

因此，不能设计成：

```json
{
  "model": "任意模型",
  "prompt": "...",
  "image": "...",
  "duration": 5,
  "ratio": "9:16"
}
```

然后假设所有 Provider 都能接受。这个设计会导致两类问题：

- 为了兼容最弱模型，把 H3/Seedance 的高级能力从产品中抹掉。
- 为了兼容最强模型，让不支持的模型静默忽略字段，用户以为控制生效但实际没有。

## 3. 目标架构

### 3.1 五个独立对象

```text
ProviderPlugin
  一个供应商 + 一个协议 Profile 的代码实现
  例：volcengine / ark_cn_v1，minimax / hailuo_v2

ModelCatalogEntry
  一个具体模型的能力清单和版本信息
  例：doubao-seedance-2.0-pro-xxxx，MiniMax-H3-xxxx

ProviderConnection
  某 Workspace 的账号、密钥、地区和 Host

ProviderModelBinding
  某账号实际允许项目使用的某一个可调用资源及其模型合同

ProjectProviderBinding
  某项目的用途使用哪个模型 Binding，或使用自动选择策略
```

这五个对象不能互相替代：

- Provider 不是模型。火山是 Provider，Seedance 是模型系列，某个 endpoint/model ID 才是可调用模型。
- 模型目录不是账号可用性。官方文档写有某模型，不代表当前账号、地区、套餐或 endpoint 有权限。
- 账号可用性不是质量合格。一个模型能请求成功，不代表它已通过人物一致性和视频漂移 Gate。
- 项目绑定不是全局默认。不同项目可以使用不同模型和不同质量策略。

还必须区分“模型身份”和“调用目标”：

```text
catalog_entry_id
  DramaForge 认识的模型能力合同，例如某个 Seedance/H3 版本

remote_resource_kind + remote_resource_id
  账号控制面可见的 model | endpoint | deployment | workflow

invoke_model_value
  按当前 protocol profile 实际写入 Wire Request `model` 字段的值
```

有的 Provider 直接用公共模型 ID 调用，有的 Provider 要先创建账号级 Endpoint/Deployment，
再把其 ID 写入 `model`。这三者不能都塞进一个含义模糊的 `model_id` 字段。

### 3.2 最终调用链

```text
快速试制 / 专业模式 / Agent
        |
        v
VideoGenerationIntent v1
        |
        v
ModelSelectionService
  - 读取项目绑定或自动选择策略
  - 过滤账号可用、能力满足、质量合格的模型
  - 形成明确的 SelectionPlan
        |
        v
ProviderPlugin.compile_video(intent, model, references, options)
  - 检查模型约束
  - 发行安全的 Artifact Reference
  - 生成供应商 Wire Request
        |
        v
ProviderRuntime.submit / poll / cancel / download
        |
        v
ProviderOperation + Artifact + Face Gate + Video Drift Gate
```

任何一次真实调用都必须能回答：

```text
谁选择了哪个模型？
为什么它是可选模型？
意图中的哪些要求被满足？哪些偏好未满足？
编译成了哪个 protocol profile 的请求？
使用了哪些 Artifact 作为参考？
这次结果经过了什么质量 Gate？
```

## 4. 模型发现、获取与选择

### 4.1 不把 `/models` 当作唯一真相

不同供应商获取模型目录的方式不同：

- 有些供应商提供可靠的模型列表 API。
- 有些只在控制台、endpoint 列表或文档中列模型。
- 有些返回模型 ID，但不返回视频能力、可选时长、参考模式和价格。
- 有些模型能力按地区、账号套餐、endpoint 配置而变化。

因此模型目录必须合并三类来源：

| 来源 | 用途 | 是否能直接启用 |
| --- | --- | --- |
| `official_static` | 由代码随插件发布的官方合同清单 | 不能，仍需账号验证 |
| `account_discovery` | 当前连接探测到的 endpoint/model 可见性 | 不能，仍需具体能力 Probe |
| `admin_approved` | 管理员按官方文档人工录入的模型 | 不能，仍需合同与账号验证 |

模型列表 API 只能证明“模型 ID 可能存在”，不能证明 `video.i2v.first_frame` 可用。

### 4.2 目录数据模型

建议新增 `provider_model_catalog_entries`。核心字段如下：

```text
id
provider_type
protocol_profile
model_id
model_revision                 供应商版本或 DramaForge manifest 版本
display_name
media_kind                     image | video | text | voice
lifecycle                      preview | active | deprecated | retired
catalog_source                 official_static | account_discovery | admin_approved
capability_manifest_json       受版本控制的能力清单
option_schema_json             受版本控制的原生高级选项 Schema
pricing_snapshot_json          仅展示/估价，真实账单仍以实际为准
documented_at
contract_manifest_hash
created_at / updated_at
```

每个 Workspace Connection 的发现结果单独保存，不直接污染全局目录：

```text
connection_id
catalog_entry_id
availability                  unknown | visible | unavailable | unauthorized
remote_resource_kind          model | endpoint | deployment | workflow
remote_resource_id
invoke_model_value            该 profile 实际提交时使用的值
discovery_evidence_id
last_seen_at
```

`invoke_model_value` 必须来自经过验证的发现结果或管理员显式绑定，不能由前端把
`display_name` 直接当成请求参数。

### 4.3 模型选择界面与 API

模型选择不应该让用户输入任意字符串。专业模式应查询一个“可用候选”接口：

```text
GET /projects/{project_id}/model-candidates?operation=video.generate
```

每个候选返回：

```json
{
  "model_binding_id": "...",
  "provider": "volcengine",
  "profile": "ark_cn_v1",
  "model_id": "doubao-seedance-...",
  "display_name": "Seedance Pro",
  "eligible": true,
  "supported_capabilities": [
    "video.t2v",
    "video.i2v.first_frame",
    "video.audio.generate"
  ],
  "unmet_preferences": ["video.last_frame"],
  "evidence": {
    "documented": true,
    "contract_tested": true,
    "account_verified": true,
    "quality_gated": true
  },
  "estimated_cost": {"currency": "CNY", "amount": "...", "confidence": "estimate"}
}
```

不满足硬要求的模型必须返回 `eligible: false` 和机器可读原因，例如：

```text
CAPABILITY_REQUIRED_MISSING: video.i2v.last_frame
REFERENCE_MODE_CONFLICT: frame_endpoints and multimodal_references
MODEL_NOT_ACCOUNT_VERIFIED
MODEL_QUALITY_GATE_MISSING
```

快速试制默认使用产品策略自动选择，但仍应把实际选择结果显示在产物侧栏；专业模式必须允许用户在候选中明确选择。

### 4.4 火山 Seedance 的实际获取与选择流程

“一个火山连接下有多个 Seedance”不能解释为 DramaForge 启动后无条件调用一个
`GET /models` 就能拿到完整真相。具体流程应为：

```text
1. Volcengine Plugin 随代码发布已核验的 Seedance ModelCatalogEntry
   -> 说明具体模型版本的能力、参数约束和 Wire Contract

2. 用户创建 Ark ProviderConnection
   -> 保存 API Key、Region、Host、protocol_profile

3. discover_account_models(connection)
   -> 若该 profile 有已验证的模型/Endpoint 列表 API，则查询账号资源
   -> 若没有可靠列表 API，则让用户从控制台选择或录入 Endpoint/Model ID
   -> 两种方式都只形成“待验证”的账号资源

4. 将账号资源与 ModelCatalogEntry 显式关联
   -> 形成 ProviderModelBinding
   -> 保存 remote_resource_id 与 invoke_model_value

5. 对 Binding 做 Contract Probe、Account Probe 和 Quality Gate
   -> 验证该账号的这个具体调用目标确实支持声明的能力

6. 项目选择 explicit Binding，或由 ModelSelectionService 从合格 Binding 中自动选择
   -> 执行时使用 Binding 的 invoke_model_value，不使用 UI 展示名
```

当前仓库的 `ark_cn_v1` Registry 对 `/models` 仍有 TODO，Volcengine Client 也只接收一组
配置固定的 image/video model 值。因此现阶段的可靠实现顺序应是：

1. 先使用插件随代码发布的官方静态目录。
2. 允许用户从火山控制台录入或选择当前账号真实可调用的 Model/Endpoint ID。
3. 逐 Binding 做账户 Probe，成功后才进入候选列表。
4. 等火山控制面模型/Endpoint 发现合同被正式验证后，再增加自动发现，不阻塞前述路径。

MiniMax 可以采用同一流程，但它的 `ProviderPlugin`、目录条目、调用目标和 Compiler
都是独立的。即使两家最终都在请求体里出现 `model` 和 `content[]`，也不能据此共享
Wire Contract。

## 5. 通用 `video.generate` 应该抽象什么

### 5.1 统一的是创作意图，不是供应商参数

建议定义内部领域对象 `VideoGenerationIntentV1`。它只包含跨模型有稳定语义的字段。

```python
from __future__ import annotations

from typing import Literal
from uuid import UUID

from pydantic import BaseModel, Field, JsonValue


class VideoGenerationIntentV1(BaseModel):
    operation: Literal["video.generate"] = "video.generate"
    purpose: Literal["shot_video", "preview", "variant"]
    prompt: str

    output: VideoOutputIntent
    references: list[ArtifactReferenceIntent] = Field(default_factory=list)
    requirements: VideoRequirements = Field(default_factory=VideoRequirements)
    preferences: VideoPreferences = Field(default_factory=VideoPreferences)
    selection: ModelSelectionIntent
    advanced: list[ApprovedModelOption] = Field(default_factory=list)
```

其中：

```python
class VideoOutputIntent(BaseModel):
    aspect_ratio: Literal["9:16", "16:9", "1:1", "adaptive"] | None = None
    duration_seconds: int | None = None
    resolution: str | None = None
    generate_audio: bool | None = None
    seed: int | None = None

class AllowedOutputSubstitution(BaseModel):
    field: Literal["duration_seconds", "resolution", "aspect_ratio"]
    policy: Literal["nearest", "at_least", "at_most", "provider_default"]
    max_numeric_delta: float | None = None

class ArtifactReferenceIntent(BaseModel):
    artifact_id: UUID
    role: Literal[
        "first_frame",
        "last_frame",
        "reference_image",
        "reference_video",
        "reference_audio",
    ]
    required: bool = True

class VideoRequirements(BaseModel):
    required_capabilities: set[str] = Field(default_factory=set)
    # 例如：{"video.i2v.first_frame", "video.i2v.last_frame"}
    preserve_character_identity: bool = False
    forbid_model_fallback: bool = True

class VideoPreferences(BaseModel):
    preferred_capabilities: set[str] = Field(default_factory=set)
    # 例如：{"video.audio.generate", "video.seed"}
    camera_motion: Literal["static", "subtle", "dynamic"] | None = None
    quality_tier: Literal["draft", "standard", "high"] | None = None
    allowed_output_substitutions: list[AllowedOutputSubstitution] = Field(
        default_factory=list
    )

class ModelSelectionIntent(BaseModel):
    mode: Literal["project_default", "explicit_binding", "auto"]
    model_binding_id: UUID | None = None
```

### 5.2 必须区分要求和偏好

这是防止“能力被悄悄降级”的关键。

| 分类 | 示例 | 不支持时的行为 |
| --- | --- | --- |
| `required_capabilities` | 必须使用首尾帧、必须保留角色参考、必须生成音频 | 直接拒绝，不发付费请求 |
| `preferred_capabilities` | 希望固定种子、希望 1080P、希望有原声 | 允许选择其他模型，但必须在 SelectionPlan 标明未满足项 |
| 供应商高级选项 | Seedance Draft、H3 特定镜头控制 | 仅对声明支持该 Schema 的模型开放 |

错误做法是把 `last_frame` 当作可选字段发给所有模型；正确做法是：

```text
last_frame.required = true
  -> 候选模型必须声明 video.i2v.last_frame
  -> 不满足则 ModelSelectionService 拒绝

last_frame.required = false
  -> 可被忽略，但 SelectionPlan 必须记录 "dropped_preference"
```

`required_capabilities` 不应完全依赖浏览器或 Agent 手工填写。Intent Normalizer 必须从
结构化意图推导能力，例如：

```text
required first_frame reference  -> video.i2v.first_frame
required last_frame reference   -> video.i2v.last_frame
required reference_video        -> video.reference.video
required reference_audio        -> video.reference.audio
generate_audio=true 且被标为硬要求 -> video.audio.generate
```

调用方额外声明的能力与系统推导结果取并集；两者冲突、引用角色重复超限或意图无法归一化
时，在模型选择前失败。这样 `references` 是事实来源，能力集合是可审计的派生约束，避免
“传了尾帧却忘记声明尾帧能力”这类绕过。

显式输出值默认也属于精确要求。用户要求 6 秒，而候选模型只允许 5/10 秒时，默认行为是
在付费提交前拒绝，不能自动改成 5 秒。只有快速试制策略或用户显式加入：

```json
{
  "field": "duration_seconds",
  "policy": "nearest",
  "max_numeric_delta": 1
}
```

才允许选择 5 秒，并在 `SelectionPlan.parameter_substitutions` 中记录请求值、实际值、
规则和选择者。`generate_audio=true` 是否可省略则由 `video.audio.generate` 位于
`required_capabilities` 还是 `preferred_capabilities` 决定。这样统一抽象既不会静默降级，
也允许快速试制在受控范围内适配不同模型枚举。

### 5.3 通用层不应有的字段

以下字段不能一开始就写死在所有视频请求中：

- `content[]`
- `first_frame_image`
- `subject_reference`
- `image_url`
- `extra_body`
- `mode: keyframes`
- 某一家供应商的草稿、服务等级或内部模型路由字段

这些是协议编译层字段，不是创作意图字段。

## 6. 保留模型特有能力的方法

### 6.1 能力清单，而非 if/else

每个 `ModelCatalogEntry` 必须发布一份能力清单。下面只展示 Schema 形态，不对应任何
已经账户验证的具体型号，不能把示例枚举直接写入生产目录：

```json
{
  "manifest_version": "2026-08-10",
  "operations": {
    "video.generate": {
      "capabilities": [
        "video.t2v",
        "video.i2v.first_frame",
        "video.audio.generate",
        "video.seed"
      ],
      "output_constraints": {
        "aspect_ratios": ["9:16", "16:9", "adaptive"],
        "duration_seconds": {"allowed": [5, 10]},
        "resolutions": ["720p", "1080p"]
      },
      "reference_constraints": {
        "first_frame": {"min": 0, "max": 1},
        "last_frame": {"min": 0, "max": 0},
        "reference_image": {"min": 0, "max": 0},
        "reference_video": {"min": 0, "max": 0},
        "reference_audio": {"min": 0, "max": 0}
      },
      "exclusive_groups": []
    }
  }
}
```

H3 V2 的能力清单可以表达其更多参考角色和互斥规则。下面的引用数量仍是结构示意，
不是 H3 全系列的已验证限额：

```json
{
  "operations": {
    "video.generate": {
      "capabilities": [
        "video.t2v",
        "video.i2v.first_frame",
        "video.i2v.last_frame",
        "video.reference.image",
        "video.reference.video",
        "video.reference.audio"
      ],
      "reference_constraints": {
        "first_frame": {"min": 0, "max": 1},
        "last_frame": {"min": 0, "max": 1},
        "reference_image": {"min": 0, "max": 4},
        "reference_video": {"min": 0, "max": 1},
        "reference_audio": {"min": 0, "max": 1}
      },
      "exclusive_groups": [
        {
          "name": "frame_endpoints_vs_multimodal_references",
          "members": [
            ["first_frame", "last_frame"],
            ["reference_image", "reference_video", "reference_audio"]
          ]
        }
      ]
    }
  }
}
```

上例的具体数量和枚举必须以该模型版本的官方文档及 Contract Fixture 为准。未填入
已验证整数上限的 manifest 不能进入 `account_verified`，也不能用于真实付费选择。
能力清单的作用是把官方合同变成可执行约束，不是替代官方合同。

### 6.2 受控的原生高级选项

仅靠通用能力集不够。模型通常还会有真实价值很高、但不适合进入全局字段的选项，例如：

- Seedance 的草稿、服务等级、镜头/音频相关控制。
- H3 的参考模式、模型特定分辨率、回调或音频控制。
- 将来本地 ComfyUI 的工作流、checkpoint、LoRA、ControlNet、采样器。

不能开放一个任意 `provider_extra_body: dict` 给浏览器或 Agent。那会产生未校验付费请求、无法审计的参数漂移和 SSRF/敏感 URL 风险。

应采用命名空间和 Schema 白名单：

```python
class ApprovedModelOption(BaseModel):
    namespace: str
    # 例如："volcengine.seedance.v1" 或 "minimax.h3.v2"
    option: str
    value: JsonValue
```

插件同时声明 `option_schema`。以下枚举仅说明 Schema 如何工作，不代表 H3 实际型号
必然支持这些组合：

```json
{
  "namespace": "minimax.h3.v2",
  "options": {
    "resolution": {"type": "enum", "values": ["768P", "1080P", "2K"]},
    "duration": {"type": "enum", "values": [6, 10]},
    "callback_enabled": {"type": "boolean", "default": false}
  }
}
```

编译器只接收通过该 Schema 校验的选项。未知 namespace、未知 option、错误枚举、与能力清单冲突的 option 必须在创建远端任务前失败。

### 6.3 产品层如何展示高级能力

- 快速试制：只展示产品认可的少量通用控制，例如模型档位、竖屏、时长、是否生成音频。产品策略自动填充原生高级选项，但要写入审计摘要。
- 专业模式：根据所选模型的 `option_schema` 动态渲染高级控制，同时显示该控制属于哪个模型。
- Agent：只能从已发布的 capability manifest 和 option schema 中选择，不能自己拼 Provider JSON。

这样既能让 H3/Seedance 的能力真正被使用，又不会让专业模式变成供应商 API 文档表单。

## 7. Seedance 与 MiniMax H3 的编译示例

### 7.1 同一个创作意图

用户希望生成一个竖屏镜头：首帧锁定演员形象，有慢速推镜，6 秒，优先带原声。

```json
{
  "operation": "video.generate",
  "purpose": "shot_video",
  "prompt": "雨夜街头，主角抬头看向霓虹灯，镜头缓慢推进，情绪克制。",
  "output": {
    "aspect_ratio": "9:16",
    "duration_seconds": 6,
    "generate_audio": true
  },
  "references": [
    {"artifact_id": "keyframe-artifact-id", "role": "first_frame", "required": true}
  ],
  "requirements": {
    "required_capabilities": ["video.i2v.first_frame"],
    "preserve_character_identity": true,
    "forbid_model_fallback": true
  },
  "preferences": {
    "preferred_capabilities": ["video.audio.generate"],
    "camera_motion": "subtle",
    "quality_tier": "high"
  },
  "selection": {"mode": "project_default"}
}
```

### 7.2 编译为 Seedance

假设一个具体、已完成账户验证的 Seedance Binding 同时声明支持首帧 I2V、6 秒、
`9:16` 和音频选项，火山插件负责：

1. 校验 `first_frame` 数量为 1。
2. 从 Artifact ID 签发短时 HTTPS Reference URL。
3. 根据该模型 manifest 校验时长、比例、音频与分辨率的组合。
4. 编译为 Ark 的 `content[]` 合同。

示意 Wire Request：

```json
{
  "model": "doubao-seedance-...",
  "content": [
    {"type": "text", "text": "雨夜街头，主角抬头看向霓虹灯，镜头缓慢推进，情绪克制。"},
    {
      "type": "image_url",
      "image_url": {"url": "https://dramaforge.example/api/v1/provider-references/<token>"},
      "role": "first_frame"
    }
  ],
  "duration": 6,
  "ratio": "9:16",
  "generate_audio": true
}
```

字段是否存在、具体枚举和值必须由该 `Seedance catalog entry + binding + profile` 的
Contract Fixture 决定。如果 6 秒或音频不受支持，SelectionService 必须拒绝硬要求，
或只对音频这类偏好记录 `dropped_preference`；不能照抄示例继续提交。当前
`ark_cn_v1` 代码已经实现基础的 `model + content[first_frame]` 提交和任务轮询；时长、
比例、音频等参数必须在实际账户 Probe 后逐项放进 manifest，不能先假定所有 Seedance
模型都一样。

### 7.3 编译为 MiniMax H3 V2

同一个意图被选到 H3 时，不应让上层改写为 H3 的字段名。MiniMax 插件负责翻译为 `/v2/video_generation` 的内容合同。

首帧模式示意：

```json
{
  "model": "<verified-h3-model-id>",
  "content": [
    {"type": "text", "text": "雨夜街头，主角抬头看向霓虹灯，镜头缓慢推进，情绪克制。"},
    {
      "type": "image_url",
      "image_url": {"url": "https://dramaforge.example/api/v1/provider-references/<token>"},
      "role": "first_frame"
    }
  ],
  "duration": 6,
  "resolution": "1080P"
}
```

若专业用户改为“首尾帧控制”，意图层只是增加一个 `last_frame` Artifact。H3 compiler 会检查：

```text
video.i2v.first_frame 已支持
AND video.i2v.last_frame 已支持
AND 当前没有 reference_image/reference_video/reference_audio
```

如果用户同时放入首帧、尾帧和角色参考视频，H3 的互斥规则会在提交前返回：

```text
REFERENCE_MODE_CONFLICT
frame_endpoints_vs_multimodal_references
```

这比“忽略其中几个参考图后继续生成”安全得多。

### 7.4 为什么这种设计不削弱能力

`video.generate` 不会丢弃 H3 的尾帧或多模态参考能力，因为这些能力首先存在于模型 manifest 中；用户和 Agent 可以通过统一的 `references[].role` 表达它们；最终 compiler 再输出 H3 原生 `content[]`。

它也不会把 Seedance 不支持的能力伪装成可用，因为 SelectionService 和 compiler 都会按照选中的 Seedance manifest 进行 fail-closed 校验。

## 8. 插件接口设计

### 8.1 当前接口的问题

当前 `ProviderAdapter` 只有：

```python
async def create(self, request: dict[str, Any]) -> dict[str, Any]
async def poll(self, remote_task_id: str) -> dict[str, Any]
async def cancel(self, remote_task_id: str) -> dict[str, Any]
async def fetch_cost(self, remote_task_id: str) -> dict[str, Any]
```

它适合 P0 快速接 Adapter，但不足以表达：

- 是图片、视频还是文本操作。
- 该模型支持哪些 capability。
- 哪些参考角色支持、上限多少、是否互斥。
- 哪些参数是要求、哪些只是偏好。
- 怎样持久化恢复某供应商的轮询上下文。
- 哪些模型特有选项可用。

### 8.2 目标插件契约

建议拆成三个职责，而不是继续扩大一个万能 Adapter：

```python
class ProviderPlugin(Protocol):
    provider_type: str
    protocol_profile: str

    def catalog(self) -> list[ModelCapabilityManifest]: ...
    async def discover_account_models(self, connection: ConnectionContext) -> DiscoveryResult: ...
    async def probe(self, request: CapabilityProbeRequest) -> CapabilityProbeResult: ...
    def build_runtime(self, connection: ConnectionContext) -> ProviderRuntime: ...


class VideoCompiler(Protocol):
    def validate(self, intent: VideoGenerationIntentV1, model: ModelCapabilityManifest) -> None: ...
    async def compile(
        self,
        intent: VideoGenerationIntentV1,
        model: ModelCapabilityManifest,
        references: ResolvedReferences,
    ) -> CompiledVideoRequest: ...


class ProviderRuntime(Protocol):
    async def submit_video(self, request: CompiledVideoRequest) -> SubmissionResult: ...
    async def poll_video(self, resume: ProviderResumeToken) -> PollResult: ...
    async def cancel_video(self, resume: ProviderResumeToken) -> CancelResult: ...
    async def download_result(self, result: ProviderResultLocator) -> DownloadedArtifact: ...
    async def fetch_cost(self, resume: ProviderResumeToken) -> CostResult: ...
```

所有结果必须是 Pydantic/TypedDict 的固定结构，不再以无约束 `dict[str, Any]` 在业务层传递。

### 8.3 编译结果和恢复令牌

```python
class CompiledVideoRequest(BaseModel):
    provider_type: str
    protocol_profile: str
    model_id: str
    operation: Literal["video.generate"]
    wire_request: dict[str, JsonValue]  # 只在插件内部/审计脱敏摘要使用
    request_schema_version: str
    safe_request_summary: dict[str, JsonValue]
    reference_artifact_ids: list[UUID]
    reference_fingerprints: list[str]

class ProviderResumeToken(BaseModel):
    provider_type: str
    protocol_profile: str
    remote_task_id: str
    remote_secondary_id: str | None = None
    query_kind: str | None = None
    opaque_state: dict[str, JsonValue] = Field(default_factory=dict)
```

`ProviderOperation` 应持久化 `ProviderResumeToken`，而不是在 Worker 中判断“如果是 Agnes 就用 `video_id` 查询，否则直接 poll”。

### 8.4 LiteLLM 的位置

LiteLLM 可以继续用于它已经稳定覆盖的 LLM/OpenAI-compatible 文本调用，也可以被某个
Provider Plugin 作为内部 SDK 使用；但不能把 `litellm.video_generation(...)` 是否存在
当作 DramaForge 视频插件化已经完成。DramaForge 仍需拥有：

- 具体模型版本的 capability manifest 与账号可用性证据。
- Artifact Reference 角色、数量、互斥和安全传输规则。
- Seedance/H3 原生参数的版本化 Compiler 与 Contract Fixture。
- 异步任务的 Resume Token、取消、下载、成本和错误归一化。
- Face Gate、Video Drift Gate、人工审阅和产物血缘。

如果 LiteLLM 对某个已验证模型完整保留这些合同，插件可在 `ProviderRuntime` 内委托给它；
若它只能覆盖公共参数或对供应商字段透传，则直接使用官方 API/SDK。无论采用哪种传输
实现，对上层的 Plugin、Manifest、SelectionPlan 和审计合同都保持不变。

## 9. 运行时的模型选择规则

### 9.1 候选过滤顺序

```text
1. 项目是否指定 explicit model binding？
2. Binding 是否 enabled？
3. Connection 是否 enabled，凭据是否仍为当前 revision？
4. 模型是否 documented + contract_tested？
5. 当前 Connection 是否 account_verified？
6. 当前用途是否 quality_gated？
7. 是否满足所有 required_capabilities 和参考约束？
8. 输出参数能否精确满足，或是否存在获准的参数替换规则？
9. 是否满足项目预算、地区、并发和内容策略？
10. 对剩余候选按项目策略打分。
```

模型评分仅用于 `selection.mode = auto`：

```text
score =
  capability_fit
  + quality_evidence_score
  + preferred_capability_fit
  + cost_fit
  + latency_health
  - queue_pressure
```

不得把评分当作静默降级理由。只要硬要求不满足，候选必须剔除。

### 9.2 回退策略

正式人物链路默认：

```text
fallback_policy = none
```

理由：换模型可能改变人物、镜头语言和成本，且可能造成一条剧中不同 Shot 的风格断裂。

快速试制可在用户同意后使用受控回退：

```text
fallback_policy = explicit_auto_for_preview_only
```

回退必须：

- 生成新的 NodeRun attempt，不覆盖原运行。
- 写入原模型、失败原因、替代模型和 SelectionPlan。
- 重新通过该替代模型的质量 Gate。
- 不得在一次 `unknown_submission` 后自动发第二个付费 create。

## 10. 对当前代码的具体改造项

当前实施决策是一次完成阶段 A+B 的统一抽象层，不再交付“管理面已经使用 Catalog，
正式执行仍读取 Agnes Settings”的长期中间状态。迁移结束后必须只有一条正式解析链：

```text
Graph Node
  -> ImageGenerationIntent / VideoGenerationIntent
  -> ModelSelectionService
  -> ProjectProviderBinding
  -> ProviderModelBinding + ModelCatalogEntry
  -> ProviderRuntimeResolver
  -> Provider Compiler
  -> ProviderRuntime
  -> ProviderOperation
```

Agnes 不是兼容例外，而是统一抽象层的第一个完整参考实现；Ark 使用同一上层合同，
但保留独立的 manifest、Compiler 和 Wire Contract。

### 10.1 必须先改的项

1. 新增模型目录与 capability manifest，而不是继续扩充 `ProviderPlugin.model_contracts`。
2. 将 `ProviderModelBinding` 从 `media_type + purpose + model_id` 扩展为关联
   `catalog_entry_id`、`capability_manifest_hash`、`remote_resource_kind`、
   `remote_resource_id` 和 `invoke_model_value`。
3. 将 `ProjectProviderBinding` 扩展到 `canonical_image`、`keyframe`、`video`、`text`、`voice`，并允许 `auto` 或 `explicit_binding` 选择策略。
4. 新建 `ModelSelectionService`，正式执行前从 Project Binding 解析模型和插件。
5. 改造 `product_path.py`：删除 `get_flux_adapter_for_workspace`、`get_kling_adapter_for_workspace` 的业务选择职责，改由 Resolver 返回 `ProviderRuntime`。
6. 将 `op.actual_provider == "agnes"` 的轮询特判改为持久化 Resume Token 后的插件通用 `poll_video`。
7. 把 `ProviderAdapter.create(dict)` 分拆成类型化的 `submit_image/submit_video`。

### 10.2 必须保留的现有能力

迁移不能破坏以下已完成的 P0 能力：

- BYOK 密钥只写不读、密钥轮换清理旧能力证据。
- 付费提交前创建 `ProviderOperation`。
- 传输异常返回 `unknown_submission`，不自动重复付费 POST。
- 远端视频任务在 429/5xx 和 Worker 重启后继续轮询同一个任务。
- Reference Artifact 仅通过 Data URI 或短时单 Artifact HTTPS 交付。
- 供应商产物 URL 立即安全下载并写入 DramaForge 对象存储。
- Face Gate、Video Drift Gate 和人工审阅仍由 DramaForge 平台负责。

### 10.3 当前不应继续扩散的旧抽象

- `flux.py` 目前是 Agnes 图像适配的历史别名，不能作为未来图片 Provider 抽象。
- `kling.py` 目前复用 Agnes 视频适配，不能作为未来可灵/通用视频 Provider 抽象。
- `workspace_credentials.settings_for_workspace_provider()` 对 `agnes/volcengine/text` 的硬编码只可作为过渡兼容层，最终应由 Plugin 根据 Connection 生成运行时配置。
- `fetch_cost()` 返回 `0 USD` 只能用于 P0 占位，不能作为多模型自动选择或预算控制的真实依据。

## 11. 分阶段实施顺序

### 阶段 A+B：统一抽象层落地（当前实施范围）

目标：模型目录、项目选择和正式 Provider 执行使用同一事实来源；同一个 Graph 无需知道
Agnes、Ark、Seedance 或后续 MiniMax 的供应商字段。

按以下顺序实施，但 A 与 B 共同组成一个交付里程碑：

1. **A1：模型目录与类型**。新增 `ModelCapabilityManifest`、
   `provider_model_catalog_entries`、版本化 `option_schema` 和目录来源；为当前 Agnes 与
   `ark_cn_v1` 固化首批 manifest、Contract Fixture、文档来源和 hash。
2. **A2：Binding 扩展与回填**。扩展 `ProviderModelBinding`，保存
   `catalog_entry_id`、manifest hash、远端资源和 `invoke_model_value`；把现有 Agnes/Ark
   Connection 与固定模型回填为明确 Binding。迁移必须可重复执行、可回滚，旧项目不能
   因回填获得未经验证的新能力。
3. **A3：候选查询**。实现模型候选 API，输出 capability、约束、四层证据、账号可用性
   和不可选原因。候选 API 与正式 Resolver 必须复用同一套资格判断，不能各写一套规则。
4. **B1：统一意图和解析器**。实现 `ImageGenerationIntent`、
   `VideoGenerationIntentV1`、Intent Normalizer、`ModelSelectionService` 和
   `ProviderRuntimeResolver`。先以无付费副作用的 shadow resolve 对照旧路径，确认解析到
   同一个 Agnes/Ark 模型；shadow 只比较 SelectionPlan，绝不调用 Provider create。
5. **B2：Agnes 迁移**。将现有 Agnes 图片、视频提交、轮询、取消、下载和成本接口包装为
   Agnes Compiler + Runtime；正式执行从 Binding 取得连接和模型，不再通过
   `get_flux_adapter_for_workspace`、`get_kling_adapter_for_workspace` 或 Agnes Settings
   选择模型。
6. **B3：Ark 迁移**。将当前 Seedream/Seedance 基础合同迁入 Ark Compiler + Runtime；
   只启用已有 Contract Test、账户 Probe 和质量证据支持的字段，不借迁移虚增模型能力。
7. **B4：统一恢复与审计**。为 `ProviderOperation` 持久化 model binding、manifest hash、
   SelectionPlan 和 Resume Token；Worker 一律通过 token 恢复 Runtime，删除
   `op.actual_provider == "agnes"` 与 `poll_persisted` 的业务特判。
8. **B5：旧路径退出**。完成等价回归后，删除 `Flux/Kling` 路由别名的业务选择职责和
   正式执行对固定模型 Settings 的依赖。兼容代码如仍需短期保留，必须标明删除期限，且
   不得成为第二事实来源。

#### 单路提交规则

- 一次 NodeRun 只能由旧路径或新路径中的一条路径拥有提交权，不能同时调用两次
  Provider create。
- Feature Flag 只能在提交前选择整条执行路径；一旦创建 `ProviderOperation`，后续轮询、
  恢复、取消和下载必须沿用已持久化的 Binding、Profile 和 Resume Token。
- `unknown_submission` 后不得切换路径、模型或 Provider 自动补发付费请求。
- shadow resolve 只允许比较解析结果和安全摘要，不能创建远端任务。

#### A+B 验收

1. Agnes 和 Ark 均由 `ProjectProviderBinding -> ProviderModelBinding -> Catalog -> Plugin`
   解析，不再由 `node_type -> Flux/Kling -> Agnes Settings` 决定。
2. 同一个 Graph 更换为另一个已验证 Binding 后无需修改节点代码；不合格模型在付费提交前
   fail-closed。
3. 每次 `ProviderOperation` 能解释 Connection、Binding、模型、manifest、SelectionPlan、
   编译摘要、引用资产和 Resume Token。
4. Worker 重启、429/5xx、取消竞态与任务恢复不会重复 Provider create。
5. 旧项目回填后实际使用的 Agnes/Ark 模型与迁移前一致，Face Gate、Video Drift Gate、
   Artifact 下载和交付 Gate 不被绕过。

#### 与 P0 的关系

A+B 是执行底座迁移，不新增 MiniMax、ComfyUI 或未经验证的 Seedance 高级能力。但它会
改变 P0 正式媒体执行路径，因此迁移前的 Provider 执行证据只能作为历史对照，不能直接
继承为迁移后的发布证据。

A+B 完成后必须在同一个干净候选提交上重新验证：付费 POST 防重、
`unknown_submission` fail-closed、Worker 恢复同一远端任务、429/5xx 轮询、Reference
Artifact 安全交付、供应商产物下载、Face/Drift Gate、10 Shot 正式黄金样本、Playwright、
Section 3.1 Gate 和运维演练。迁移完成且这些证据重新通过前，P0 仍不能标记完成。

### 阶段 C：扩展火山 Seedance 的多模型能力

目标：一个 Ark Connection 可按模型能力选择，而不是只使用配置中的单模型字符串。

- 用真实账户完成每个候选 Seedance 模型的 Probe。
- 将时长、比例、分辨率、音频、首帧等能力逐模型录入并 Contract Test。
- 专业模式生成动态高级控制；快速试制只开放安全的产品预设。
- 为每个模型单独记录质量证据，禁止“一个模型通过 Gate 后整家火山都算合格”。

### 阶段 D：接入 MiniMax Image/H3 Video 原生插件

目标：验证该抽象确实没有因通用化而损失 H3 能力。

- 新增 `minimax/hailuo_v2` Protocol Plugin。
- 实现 H3 `first_frame/last_frame/reference_image/reference_video/reference_audio` 的能力 manifest 和互斥校验。
- 实现 V2 创建、任务查询、文件下载、取消和成本归一化。
- 首先完成 Contract Test，随后进行付费 Account Probe 和质量 Gate。

### 阶段 E：本地模型与 ComfyUI

目标：把本地算力纳入同一选择机制，而不是把 ComfyUI 当作特殊旁路。

- `comfyui_local_v1` 作为 Protocol Plugin。
- 每个 Workflow/Checkpoint/LoRA 组合是一个内部 Model Catalog Entry，不把所有工作流伪装为同一个模型。
- Capability manifest 描述工作流实际输入槽位，例如 ControlNet、IP-Adapter、首尾帧、音频驱动。
- 产物、排队、GPU 显存、工作流版本、模型哈希进入 ProviderOperation 审计。

## 12. 完成标准

模型能力插件化达到合格状态，至少满足以下条件：

1. 新增一个 Provider/Protocol Profile 不需要修改 ConnectionService、ProductPath 或前端固定 Provider 分支。
2. 一个 Provider 下新增模型不需要改数据库 schema 或硬编码用途模型 ID，只需增加目录条目、manifest 和 Contract Fixture。
3. 项目实际执行只依据 Project Binding/SelectionPlan 解析模型，不能继续默认 Agnes/Kling/Flux。
4. 所有硬性创作要求都在发起付费请求前由 manifest 校验；不支持必须 fail-closed。
5. 所有模型特有高级参数都具有版本化 Schema、UI/Agent 校验和脱敏审计记录；不接收任意供应商 JSON。
6. 每次 ProviderOperation 都可以复现选择：Connection、Binding、Model、Manifest、Profile、编译摘要、Reference、Resume Token、成本与质量证据齐全。
7. Seedance 与 MiniMax H3 都可以各自发挥首帧、尾帧、多模态参考等原生能力，不需要为了“通用接口”损失能力。

## 13. 最终决策

采用：

```text
统一意图 + 模型能力目录 + 受控高级选项 + Provider 编译器 + 证据驱动选择
```

不采用：

```text
所有供应商共用一套平铺 JSON 参数
```

前者既能让个人创作者在快速试制中少操作，又能让专业模式暴露真实可控的模型能力；更重要的是，它能让 Agent 在可验证的能力边界内做选择，而不是猜测某个模型“应该支持什么”。

当前实施范围采用：

```text
阶段 A+B 作为一个统一抽象层里程碑
  -> 目录、Binding、Selection、Compiler、Runtime、Resume 和审计一起闭环
  -> Agnes 与 Ark 首先迁入
  -> 旧专用路由完成回归后退出
```

不采用“先长期上线阶段 A、正式执行继续独立读取 Agnes 配置”的双轨架构。阶段 A 只可
作为 A+B 内部迁移检查点，不是本轮最终完成状态。
