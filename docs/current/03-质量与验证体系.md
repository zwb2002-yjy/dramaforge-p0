# DramaForge 质量与验证体系

**状态：ACTIVE / 发布质量合同**

**版本：1.0**

**日期：2026-08-12**

## 1. 质量承诺

DramaForge 不承诺“生成前准确预测成片”或“永不出废片”。第一版承诺的是：

> 在生成前暴露已知风险和能力缺口；用代表镜头降低全量试错成本；生成后用多层证据定位问题；用户可比较修复方案并只重跑受影响部分。

首版“可用作品”的四个用户维度：

1. **人物**：不换身份、没有不可接受的脸/身体崩坏、对白角色不串；
2. **叙事**：剧情看得懂、镜头衔接合理、故事在 15–30 秒内闭环；
3. **画面**：无恶性生成幻觉，风格和光影大体一致；
4. **音频**：人声清晰、声线稳定、说话人正确、嘴部有基础同步。

这些维度必须由自动证据与人工判断共同验收，不能压缩成一个总分。

## 2. 六层质量系统

### Q0：授权与能力完整性

在请求发出前检查：

- 用户是否授权本次费用，累计预计值是否在上限内；
- 模型是否声明并经验证支持所需模态、画幅、时长、参考图/首尾帧、原生音频等能力；
- Provider 插件是否能无损表达必要参数；
- 参考资产是否可读、格式正确且允许用于该模型；
- 模型、权重、声音和其他资源的许可是否满足发布方式。

这里失败必须阻断。不能因为 Prompt 里写了角色描述，就把不支持参考图的模型当成“人物一致性方案”。

### Q1：有效请求完整性

每次外部调用保存脱敏后的证据：

- 供应商、端点、模型和版本；
- Provider 无关 Intent 的哈希；
- 实际发送的画幅、时长和受支持高级参数；
- 每个参考资产的 Artifact ID、哈希、角色绑定和注入位置；
- 被应用、降级、忽略和拒绝的参数；
- 幂等键、请求/响应标识、费用与时延。

`TranslationReport` 出现必需参数丢失时阻断。第一批开发首先用 Spy Provider / Contract Test 证明 Canonical 图像的字节或 URL 真正进入有效请求，而不是先调阈值。

### Q2：制品完整性

确定性检查：

- 文件能否解码；
- 尺寸、画幅、帧率、时长、音轨和编码是否满足计划；
- 黑帧、全静帧、静音、截断、缺帧和损坏；
- 必需交付物是否齐全，哈希是否一致。

这类错误是不可覆盖的硬 Gate。

### Q3：人物、外观与时序一致性

至少分开记录：

- Canonical 角色资产、Shot Reference Binding 与有效请求证据；
- 镜头中角色数量和说话人归属；
- 发型、服装、年龄感、体型和显著身份锚点；
- 首帧、关键帧、末帧的身份与外观漂移；
- 遮挡、侧脸、远景和多人场景下的“不足以判断”；
- 身体/手部/面部严重异常。

双人同框必须额外复核“每条手臂和手属于谁”：肩膀、躯干或背后发生交叉遮挡时，
若肢体无法明确归属、从另一角色身体穿出、出现额外手臂/手或人物数量不符，标记
`unexpected_person_or_limb`。这类缺陷即使文件可解码、身份血缘完整，也不得自动通过；
人工明确观察到严重穿模时，当前镜头验收结论为拒绝，只允许局部重拍或用户填写理由后
显式覆盖，不能以平均漂移分数或首末帧正常掩盖中间帧缺陷。

首版不计算人脸 embedding、身份相似度或替代分数。没有可信且校准过的自动评估器时，结果必须是 `needs_human`，不能自动放行。

### Q4：声音、口型与表演

- 音频可懂度、噪声和削波；
- 同一角色的声线稳定性与不同角色可区分性；
- 说话人和剧本对白归属；
- 语音时长与镜头时长；
- 口型/语音时间对齐信号；
- 表情、视线、动作和对白情绪是否明显冲突。

检测器能力不足时输出 `insufficient_evidence`，转试拍人工验收，不得自动判通过。

### Q5：叙事、镜头和成片连续性

- 对白是否遗漏、重复或串人；
- 关键剧情是否有落地镜头；
- 镜头顺序、空间、动作、视线、道具与场景是否突变；
- 节奏、转场、字幕和声音混合是否影响理解；
- 开头冲突与结局是否形成闭环。

### Q6：用户验收

试拍和成片必须由人查看。系统展示证据、已知缺陷和建议，用户选择：接受、覆盖主观 Gate、选择修复或放弃。用户覆盖会保留原因、操作者、版本和时间，不能篡改自动检测原值。

## 3. GateDecision 语义

```text
pass                证据足够，满足当前质量策略
warn                有缺陷但不阻塞，用户可继续
needs_human         自动证据不足或主观冲突，必须人工决定
block               文件/授权/安全/必需能力等硬失败，不可覆盖
```

身份、外观、表演、口型和审美通常是 `warn` 或 `needs_human`，允许用户查看证据后覆盖。损坏文件、缺少必需产物、预算未授权、安全/合规失败、必需参考参数未发送为 `block`。

质量策略按 `quality_policy_id + version` 绑定模板、节点与模型能力档案。修改策略不能改变历史结果。

## 4. 人物一致性的首版证据路径

首版固定执行：

```text
Canonical Character Asset
→ Shot Reference Binding
→ Provider Capability
→ EffectiveRequest / TranslationReport
→ Generated Artifact
→ identity_review
→ 视频首/中/末帧证据
→ 用户试拍验收
→ Issue / 局部修复
```

`identity_review` 只校验两份独立产物和参考血缘，不能自行声称人物一致。Canonical 缺失、生成产物缺失或同一 payload 被伪装成两源证据时返回 `blocked`；证据完整但尚未人工判断时返回 `needs_human`。人物、发型、服装、体型、跨帧变化及表演由试拍验收判断。

若未来引入自动视觉评估器，必须使用许可清晰的模型和权重，报告覆盖率、分桶误差、与人工判断的冲突样例，并通过单独的产品发布决策。首版允许完全没有自动人物评估器，但不允许伪造通过结果。

## 5. 人物一致性校准集

8 月 26 日前建立版本化评测集 `character-consistency-v1`。测试角色只使用明确可测试的虚构角色资产，至少覆盖：

- 相同身份：正面、左右侧脸、不同表情、不同光照、近/中/远景；
- 合理可变：同一人物的姿态、表情和允许的服装变化；
- 不同身份：相似年龄/发型/性别表现的困难负样本；
- 明显错误：换脸、双脸、五官融合、年龄突变、服装/发型锚点丢失；
- 视频：首/中/末关键帧、短暂漂移、末帧漂移、遮挡后重现；
- 双人对白：身份串位、说话人串位和同框误关联。

每个样本由至少两次独立人工标注；分歧由负责人裁决并保留理由。标签不是“美/丑”，而是：

```text
same_character_acceptable
same_character_unacceptable
different_character
severe_artifact
insufficient_evidence
```

## 6. 工程验收方法

首版评测集用于验证从 Canonical、Reference Binding、EffectiveRequest、Artifact 到人工验收和修复的闭环：

- 参考资产是否真实进入有效请求；
- 图片和视频证据是否可回溯到对应角色、镜头、模型和请求；
- 首/中/末帧是否可供并列人工复核；
- 人工接受、拒绝和重生成是否保留理由、范围、版本和操作者；
- 一致性问题能否形成 Issue，并只重跑受影响节点；
- 不同 Provider 和镜头类型的失败模式是否形成可复用能力档案。

若未来评估候选自动视觉模型，再单独报告覆盖率、precision/recall、分桶结果和与人工判断的冲突样例；这些指标不是首版发布硬要求。

## 7. 代表镜头试拍

代表镜头不是随机第一镜。确定性评分结合：

- 主角正面可见且有对白；
- 人物一致性和口型风险；
- 动作、表情和镜头运动复杂度；
- 多人同框/遮挡/回头等风险；
- 是否代表主视觉、光影和关键场景；
- 能否同时验证最多关键假设。

AI 导演解释选择理由。快速模式默认选择，专业模式允许用户改选。试拍验收卡并列展示原计划、参考资产、成片、关键帧、音频/口型证据、自动检测的局限和人工问题清单。

## 8. 生成前风险预审

`RiskReport` 由版本化规则、模型能力档案和结构化分镜产生。首版规则至少覆盖：

- 角色数量、多人物同框和相似外观；
- 快速动作、复杂肢体、拿取小物件；
- 长对白、语速与镜头时长不匹配；
- 角色正面对白和口型要求；
- 遮挡、回头、出画再入画；
- 跨镜头服装、场景、时间和光线变化；
- 不受模型支持的画幅、参考方式、首尾帧或高级参数；
- 预计费用高但信息增益低的镜头。

对于不提供人物数量锁、手部/骨骼修复或 negative prompt 原生字段的视频模型，系统只能
在有效 Prompt 中加入正向构图约束，不能伪造供应商参数。双人镜头默认要求人物恰为两人、
肩线清晰、肢体保持在各自一侧、避免越肩交叉/拥抱/触碰，并优先使用稳定体位和轻微次级
运动。Prompt 约束只降低风险，不替代生成后的全时段抽帧和人工验收。

每项显示证据、严重度、已知/未知、推荐修改和是否必须试拍。预审只能降低已知风险，不能把概率包装成质量保证。

## 9. 修复规划

`RepairOption` 必须是可执行 Command 草案：

```json
{
  "cause": "镜头 3 末段身份漂移，参考注入完整，动作遮挡后恢复失败",
  "strategy": "拆分镜头并降低遮挡复杂度",
  "changes": [],
  "rerun_nodes": [],
  "reused_artifacts": [],
  "expected_improvement": "medium",
  "remaining_risks": [],
  "added_cost": {},
  "estimated_time": {},
  "evidence_refs": []
}
```

首版修复来源是平台维护的版本化规则和模型能力档案，不声称自动学习。必须记录用户选择、结果和回退，为以后形成经验数据。

## 10. 发布测试金字塔

### 合同与单元测试

- Skill Schema、状态机、确认、预算、版本与影响分析；
- Provider 编译与参数翻译；
- 质量策略和 GateDecision；
- 局部失效和 Artifact 复用。

### 集成测试

- PostgreSQL、Outbox、Arq、MinIO、Provider Mock/Spy；
- 参考资产实际进入请求；
- 超预算、取消、超时、失败恢复；
- 两种 ShotGraphTemplate。

### 真实 Provider 黄金样本

- 冻结 Intent、参考资产、模型/端点版本和期望结构，不冻结像素相等；
- 每次记录费用、时延、有效请求、关键质量信号和人工结论；
- 同一代码提交完成创作、试拍、正式生产、修复、导出全链。

### 浏览器 E2E

- 三入口、四阶段、四确认、自然语言变更预览；
- 快速/专业模式共用事实；
- 预算越界、质量失败、局部修复和下载；
- 以 DOM、网络、控制台和业务断言为主，截图仅作证据。

### 无主持用户测试

开发者只能观察和记录，不能告诉用户点哪里。记录完成时间、卡住位置、误解、回退、最终作品和用户原话；测试后按严重度进入修复队列。

## 11. 质量发布 Gate

9 月 15 日放行前必须有：

- Q0–Q6 每层的自动或人工证据；
- 人物一致性校准报告，不再只有演示样本；
- Canonical 参考注入的 Contract Test 和真实请求证据；
- 至少一个身份漂移、一个口型/声音问题和一个叙事问题的定位与修复演练；
- 人物自动评估器若存在，其模型、权重、数据来源与许可清单；首版没有自动评估器时必须有完整人工试拍证据；
- 三名目标用户的无人代操作结果；
- 负责人签署的已知限制与不宣传清单。

任何一项缺失，都只能发预览/实验版本，不能标记为“核心体验稳定”。
