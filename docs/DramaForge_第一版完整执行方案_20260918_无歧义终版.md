# DramaForge 第一版完整执行方案（最终定稿版）

> 基线：执行开始时重新确认 `origin/dev` 的准确提交版本  
> 目标：当前二维专业制作工作台全部完成并稳定后，统一作为第一版发布。  
> 纪律：一个阶段只解决一类问题；先证明问题存在，再做最小修改；禁止边搬架构、边加功能、边大改界面。

---

# 零、执行权威与阶段判定

本执行方案只负责“怎么做、怎么证明完成”；产品 / 数据 / 运行时语义以配套《第一版完整设计方案》为准。

执行时先区分：

```text
当前事实：代码、迁移、OpenAPI、测试、8080 运行证据
目标合同：设计方案
执行方法：本执行方案
```

仓库治理规则、受保护分支规则或强制合同不得被静默绕过。发现冲突时先记录冲突并停在当前阶段，不得让 Agent 自己选择一种语义继续。

所有阶段状态最终只能使用：

```text
已验证，无需修改
已确认问题，待修复
已修复并通过
非第一版阻塞项，延期
阻塞，未通过
```

“持续执行”只约束第一版 **Goal 编排层**；单个 Task 仍必须 bounded：只解决一个问题、限制 Owned Scope、完成最小验证并形成 review checkpoint。Task review 通过后，编排层无需等待新一轮人工提示即可继续下一个已授权 Task。禁止用“持续执行”为理由让一个 Task 无限扩大 diff，也禁止用“Task 完成”为理由停止整个第一版 Goal。

# 一、全局语言要求

整个项目的用户可见文字统一使用中文创作语言。

禁止普通创作者界面直接出现内部实现标识：

```text
代码类名
接口字段名
数据库字段名
供应商原始参数名
内部状态机名
哈希
内部协议 / 能力键名
开发术语
```

不是“禁止英文”。模型名、供应商名、模型版本、MP4 / SRT 等必要专有名词可以保留；但不能把原始 schema 字段当成产品控件。

内部代码仍可保留真实标识，但不得直接透传给用户。

普通界面将内部技术概念转换为：

```text
生成任务
模型执行
候选结果
正式版本
导演建议
创作技巧
画面风格
导演方式
参考素材
生成描述
生成失败
重新生成
```

高级创作设置也必须使用创作语义，不得退化成供应商参数面板。

供应商 / 模型 / 模型版本属于用户实际选择与结果来源的一部分，可以正常展示。原始技术字段、运行编号、请求摘要、血缘与错误码可以存在于**开发 / 诊断详情**中，但必须满足：

```text
只读
默认隐藏
明确标注为开发 / 诊断信息
不作为普通创作操作入口
不参与普通用户的参数编辑
```

# 二、底层参数隔离执行要求

这条规则贯穿所有后续阶段：

```text
用户界面
→ 创作产品模型
→ 接口适配层
→ 后端业务模型
→ 模型适配层
→ 供应商参数
```

任何任务如果新增或修改以下内容：

```text
供应商参数
接口字段
数据库字段
内部状态
模型能力字段
运行编号
错误码
```

必须同时检查：

```text
是否绕过前端接口适配 / view-model 层，被页面组件直接依赖？
是否被普通界面直接显示？
是否被直接做成输入控件？
是否只是把英文参数翻译成中文后继续暴露？
```

只要答案为“是”，就不通过验收。

普通界面只能接收已经转换后的创作语义，例如：

```text
角色参考
镜头运动
画面比例
生成时长
当前正式版本
生成失败原因
下一步建议
```

模型差异必须在适配层消化。

错误也必须经过产品化映射后再显示。



# 三、执行前置：基线再验证

整个计划开始前先建立一次 Baseline Manifest；每个阶段开始时只刷新与该阶段有关的项：

```text
origin/dev 准确提交版本
Git tree / 工作区状态
当前数据库迁移头
当前 OpenAPI / 前端生成类型状态
当前正式 8080 部署状态
当前 required checks / CI 名称
相关本地测试命令与最近结果
当前容器镜像 / Compose 身份
```

同时建立“Gate → 实际证据”映射，避免只写抽象的“测试通过”：

```text
Gate
→ 对应命令 / CI check 名
→ 输入环境
→ 期望结果
→ 证据位置
```

后续仓库若修改了 CI 名称或测试命令，先更新 Baseline Manifest，再执行 Gate；不得让计划中的旧名字取代仓库真实配置。

如果 `dev` 已经前进，不自动推翻整份方案，也不得机械执行旧结论。

只重新审查受影响阶段，并使用统一阶段状态；发现问题先标记 `已确认问题，待修复`，修复与 Gate 都通过后再变为 `已修复并通过`。

所有阶段都遵循“先验证、后修改”。阶段 1～3 尤其如此：没有真实双职责、双事实源或行为风险，不为了结构整齐而重构。阶段 0 如果最新 `dev` 已经精确审查正确，也直接以证据通过，不重复实现。

以下动态值必须由执行时实证填充，不允许从旧计划猜：

```text
当前 SHA / tree
正式 Provider / Model Manifest 条目
required CI checks 与本地命令
支持的 pre-release migration baseline
宿主平台 / CPU 架构
单用户资源实测值
镜像 digest
```

拿不到证据时状态只能是 `已确认问题，待修复` 或 `阻塞，未通过` / 待验证，不得假定通过。

# 阶段 0：候选 / 修复候选精确审查

## 目标

先验证最新 `dev` 是否仍存在该错误；存在才修复，不存在则用自动测试和 8080 证据直接通过。

要防止的问题：

```text
正式视频甲
→ 修复
→ 候选视频乙
→ 用户点击审查乙
→ 页面实际却显示甲
```

## 需求

建立统一审查目标：

```text
项目
镜头
具体媒体结果
生产阶段
审查类型
来源
修复请求（可选）
修复步骤（可选）
```

其中：

```text
具体媒体结果
```

是唯一审查身份。

修复步骤需要能够读取：

```text
对应生成任务
结果媒体
任务状态
审查决定
下一步
```

页面支持精确进入某个候选结果。

错误目标直接报错，不得自动退回当前正式版本。

## 允许改动

```text
审查后端
修复结果读取
审查页面
候选结果跳转
相关测试
```

## 禁止

```text
第二套候选系统
第二套审查系统
新修复执行系统
自动设为正式版本
复杂局部视频修补
```

## 验收

普通候选：

```text
候选甲
→ 精确审查甲
→ 批注甲
→ 决定甲
→ 用户显式设为正式版本 / 已有明确自动授权规则采用
```

未审查候选不能通过普通 UI 直接成为正式版本；审查通过也不能在无授权时自动 Formal。

若 AUTO 允许自动 Formal，必须同时证明：审查决定精确绑定当前 artifact、decision 为可采用状态、review 未 stale、候选仍属于当前 project / shot / stage、当前 policy revision 允许该动作、Formal 写入通过版本 / stale gate。Reject / Needs Repair / 迟到审查 / 已撤销 policy 均不得触发自动采用。

修复候选：

```text
正式甲
→ 修复
→ 候选乙
→ 审查乙
```

必须：

```text
播放器 = 乙
审查依据 = 乙
批注 = 乙
决定 = 乙
甲的迟到请求不能覆盖乙
```

```text
连接
会话
事务
```

```text
新万能数据库服务
```

```text
跨工作区访问拒绝

生产工作进程重启后权限范围恢复正确
导演工作进程重启后范围恢复正确

事件归属正确
```

# 阶段 3：供应商模块职责收口

## 目标

每个模型供应商只保留一条正式执行方式。

内部链：

```text
模型目录
→ 模型绑定
→ 模型适配
→ 请求编译
→ 执行
→ 网络通信
→ 模型结果
```

## 任务

对较重供应商模块拆清：

```text
请求编译
执行控制
网络通信
数据结构
```

## 禁止

```text
改变接口地址
改变认证方式
改变参数含义
新增偷偷备用供应商
偷偷切换模型
图片视频使用同一套错误参数
保留旧执行方式和新执行方式同时可用
```

## 第一版模型支持 Manifest

先从当前 Catalog / Binding / UI 暴露面生成 `FirstReleaseModelManifest`，明确哪些供应商 / 模型 / 版本属于第一版正式支持。Manifest 外能力不能因为“代码里有 adapter”就自动算正式支持。

同时闭环连接配置：

```text
新增 / 更新供应商连接
→ 服务端保存密钥
→ 测试连接
→ 建立模型绑定
→ 能力校验
→ 项目 / 镜头可选择
```

密钥不得明文回传前端、写日志、写 Release Manifest 或打进镜像。

## 验收

每个 Manifest 中正式支持的模型验证：

```text
图片生成
视频生成
参考图
首帧
尾帧
模型原生控制
不支持能力
轮询
取消
重试
```

同时必须验证：

```text
供应商字段不会直接进入普通用户界面
不同模型的字段差异由模型适配层统一消化
前端只接收统一创作语义
普通界面不存在原始参数表单
普通界面不存在供应商原始错误码
```

建立 `ProviderValidationMatrix`。每个 `FirstReleaseModelManifest` 条目声明 `contract / real_smoke / release_golden` 验证级别：所有正式模型至少有 deterministic contract；每种正式 Provider / 独立 transport 至少有足够 real smoke；最终图片 / 视频主路径至少各有 release golden。Manifest 中每个正式 Provider × 实际使用的媒体路径（image / video）至少有对应 transport 证据；同一 transport 下的具体模型参数优先使用 deterministic fixture / captured request，只有无法由 fixture 证明的真实 wire / 独特能力才增加付费 smoke。真实请求必须与预期一致。

# 阶段 4：物理目录整理判定（条件阶段）

## 目标

先判断物理目录是否已经造成真实的职责混淆、双执行入口、错误依赖方向或维护风险。

**目录“不够漂亮”本身不是第一版发布阻塞项。**

## 判定

只有出现以下任一情况，才在第一版执行目录迁移：

```text
同一事实因目录归属不清存在多个写入口
旧模块与正式模块同时可被调用
错误 import 让业务绕过正式 owner
目录结构直接阻碍阶段 1～3 的职责收口
安全 / 权限 / Provider authority 因物理结构无法证明唯一
```

如果上述问题均不存在：

```text
结论 = 非第一版阻塞项，延期
不做大规模 move / rename
继续阶段 5
```

如果必须执行，目录应表达：

```text
访问控制
素材
导演
剪辑
执行
生产
模型供应商
审查
交付
维护
公共能力
```

## 只允许

```text
移动文件
改文件名
改导入路径
清理模块导出
更新开发文档
```

## 禁止

```text
改业务逻辑
改数据库
改接口语义
改状态机
改模型请求
顺手增加功能
```

## 验收

若执行迁移，必须：

```text
接口定义不变
前端生成接口类型不变
数据库迁移为零
模型请求不变
受目录迁移影响的完整构建 / import / 单元与集成 Gate 通过
业务行为不变
无需因此重复 RC 级 Computer Use / 付费 Golden，除非无法证明影响边界
```

本阶段按统一状态收口：

```text
无需迁移 → 已验证，无需修改
完成必要迁移 → 已修复并通过
纯结构美化 → 非第一版阻塞项，延期
必要迁移未完成 → 阻塞，未通过
```

完成判定后结束第一版结构美化工作。

# 阶段 5：外部创作知识审查 + 统一创作能力结构

## 目标

把已有创作能力系统升级为长期可扩展的正式体系，同时冻结**有限的第一版创作能力 Manifest**，避免来源审查变成无限收集。

本阶段结束必须输出：

```text
FirstReleaseCreativeCapabilityManifest
→ 第一版正式创作类型
→ 画面风格
→ 导演方式
→ 创作技巧
→ 每项版本 / 来源 / 许可证 / E2E 状态
```

外部来源只为补齐这份 Manifest 服务；Manifest 外内容进入 backlog，不继续扩张第一版。

采用“最小代表集”原则：Manifest 内已有同类能力尚未完成真实 effect chain 前，不继续新增同类风格 / 技巧凑数量。

## 外部来源审查

评估：

```text
导演技巧类项目
影视生成描述类项目
摄影知识类项目
视频工作流类项目
已有创作技巧库
```

每个来源记录：

```text
仓库
许可证
来源版本
可吸收知识
可吸收方法
可吸收结构
不可接入的外部执行方式
重复能力
建议合并到哪个正式创作技巧
```

## 来源治理

新增统一来源记录：

```text
来源名称
来源地址
许可证
来源版本
导入时间
导入方式
```

导入方式：

```text
直接吸收
改造吸收
仅作参考
```

许可证不明、与当前分发方式不兼容或具有强 copyleft 风险的来源默认“仅作参考”。禁止因为仓库公开就默认可以复制文本、代码或资源。实际进入发行包的内容必须保留来源版本和许可证证据。

## 统一创作技巧结构

至少：

```text
唯一标识
版本
来源
许可证
适用阶段
必须上下文
可选上下文
冲突关系
兼容关系
输入
输出
实际作用
质量要求
修复方式
```

# 阶段 6：创作技巧推荐 / 组合 + 有效创作意图

## 目标

让创作能力真正进入导演规划和生产计划。

## 推荐依据

系统根据：

```text
用户意图
当前制作阶段
创作类型
画面风格
导演方式
当前镜头
已有素材
模型可用能力
```

推荐创作技巧。

## 三种创作模式

自动：

```text
用户先明确授权范围
→ 导演系统在授权范围内推荐并推进
→ 超出范围时重新请求用户决定
```

自动模式不是无限授权。模型切换、正式版本采用、自动重试等高影响动作只有在用户事先明确授权时才可自动发生，并必须留下授权 / 决策记录；超出授权范围、扩大修改范围、违反硬约束或发生未声明降级时必须暂停。

辅助：

```text
导演推荐
→ 用户确认
```

手动：

```text
用户自己选择
```

三种模式共用同一套：

```text
创作技巧库
推荐逻辑
技巧组合
创作意图编译
生产链
```

创作模式是项目级默认 policy；切换模式只影响后续确认 / 自动推进策略，不能复制项目、创建第二套 Scene / Shot 或重写已有 Formal。若需要局部差异，只保存场次 / 镜头 policy override。

第一版 AUTO 不新建自动视觉 QA Runtime：允许在授权范围内自动规划、生成、恢复，但候选仍进入同一 Exact Review checkpoint；存在审查决定后，才可以按预授权规则自动 Formal。

任何预授权必须来自可版本化、可撤销、可查看的 `Authorization Policy`（可复用当前正式模型，只要求语义成立），至少记录 scope、allowed actions、Provider / Model 范围、retry limit、Formal 自动采用条件、硬约束、revision 与撤销状态。每次自动动作都必须记录命中的 policy revision；stale / revoked / scope mismatch policy 不得授权。

## 冲突

例如：

```text
长镜头倾向
vs
快速蒙太奇
```

必须明确告诉用户有冲突。

不得系统偷偷删掉其中一个。

AUTO 模式只有在用户预先授权了明确冲突策略、且该策略不会违反硬约束时，才可自动选择，并必须记录 resolution provenance；否则暂停等待用户决定。

## 有效创作意图

至少包含：

```text
故事意图
画面意图
镜头意图
表演意图
连续性要求
参考素材策略
生成描述指导
生成限制
质量要求
修复指导
来源记录
```

## 生效范围与优先级

按“字段 / 创作维度”解析，而不是整个对象覆盖：

```text
镜头级同字段
> 场次级同字段
> 项目级同字段
> 模板 / 默认值
```

镜头只改景别时不得抹掉项目画面风格；清空必须有显式 unset / inherit 语义。

导演建议**不是独立于范围之外的一层优先级**。

用户接受导演建议后，必须把它落成目标范围内的正式覆盖，例如：

```text
镜头级覆盖（来源：已接受导演建议）
场次级覆盖（来源：已接受导演建议）
项目级覆盖（来源：已接受导演建议）
```

同一范围、同一字段内：

```text
最新有效 explicit revision
（用户直接编辑或用户接受的导演建议）
> 尚未接受的推荐 / 模板
> 默认值
```

用户接受导演建议后，该值物化为新的 canonical explicit override；`source` 仅保留 provenance。旧的用户手动值不能因为“来源更高”压住后来明确接受的建议；反过来，用户后续再手动修改则由更新 revision 生效。所有 apply 必须继续通过 stale / base revision gate。

## 验收

同一输入做 A/B：

```text
甲：不启用目标风格 / 技巧
乙：启用
```

必须观察到：

```text
有效创作意图按声明 effect 发生变化
来源记录不同
目标 effect 对应的下游事实发生变化
```

例如 camera effect 应改变镜头 / camera intent；reference effect 应改变 ReferencePolicy；review-only skill 可以只改变审查要求，不能强制要求所有 Skill 都改 Shot Design。

同时验证三种模式：

```text
MANUAL：用户选择直接进入同一 compiler
ASSIST：推荐必须经用户确认
AUTO：只在授权范围内推进，越界暂停
模式切换：不复制生产事实，不改变既有 Formal / Artifact
```

三种模式仍走同一条生产执行链。

进入执行计划时必须冻结：

```text
有效创作意图
风格 / 导演方式 / 技巧版本
参考素材版本
Compiler 版本
模型能力 Manifest 版本
模型 / Provider Binding
授权与降级决定
```

随后修改项目配置不得改变已经创建的 NodeRun / Artifact 解释。

# 阶段 13：功能冻结 + 发布候选建立

# 阶段 13-A：DeepSeek + Agnes 持续执行授权

## 目标

```text
“先到这里”
“后面以后再做”
“等待下一轮再继续”
```

除非已经达到 `RELEASE_DONE`，或者存在无法由当前执行环境自行解除的外部硬阻塞。

## 合并与发布身份

```text
开发分支最终候选
→ 全部必要检查通过
→ 最终审查
→ 合并主分支
→ 验证 main 发布提交与已验证候选的运行内容身份
→ 发布标签
→ 第一版发布
```

如果 merge / squash 只改变 Git 提交身份而**没有改变运行相关文件内容**，允许继承候选运行证据，但 Release Manifest 必须同时记录：

```text
validated_source_commit
main_release_commit
运行内容 / Git tree 身份
最终镜像摘要
```

如果 main 合并引入任何运行相关 diff，或最终镜像被重新构建且摘要变化无法证明等价，则建立新的发布候选并重新执行受影响 Gate；无法证明影响边界时重跑阶段 13～15。

Release tag 必须指向最终 main 发布提交。

若 main 合并仅改变 Git commit 身份而运行内容完全一致，优先继续发布已经完整验证的 RC 镜像；不要为了 source label 漂亮而重建。任何重建产生的新 digest 都视为新的发行物，必须证明等价或重新执行受影响 Gate。

## 完成条件

进入本阶段前必须已经达到 `RELEASE_READY`：所有发布阻塞项通过，最终候选证据一致。

阶段 4 若已经证明只是非阻塞目录清理，可以明确记录为：

```text
非第一版阻塞项，延期
```

不得因为这一项延期而把真实可发布版本继续拖住。

只有最终发布候选的代码、镜像、迁移、8080 验收、Recovery、真实模型验证与安装证据能够对应，并且 tag / Release Manifest / 第一版发行物已经发布，才进入：

```text
RELEASE_DONE
DramaForge 第一版完成
```

# 代理执行纪律

每个任务必须写明：

```text
目标
当前证据
影响的 authority / canonical fact
负责文件（审计后再精确列出）
必须修改
明确不做
风险
测试命令 / CI Gate
验收条件
```

不能在未检查最新 `dev` 前凭旧文档机械指定文件；Owned Files 必须来自当轮代码证据。

禁止：

```text
同时推进多个主阶段
顺手清理邻接模块
为了通过测试降低验收标准
未证明旧逻辑无用就直接删除
建立临时第二套事实源
```

每个阶段完成后先审查，再进入下一阶段。

阶段状态必须明确使用：

```text
已验证，无需修改
已确认问题，待修复
已修复并通过
非第一版阻塞项，延期
阻塞，未通过
```

不得为了“完成阶段”强行制造代码变更。

# 最终执行原则

> 先把候选审查和底层事实边界收干净；  
> 再把画面风格与创作技巧做成真正生产能力；  
> 再让导演助手成为可持续对话的制作助手；  
> 再把当前二维工作台做成连续、自然、不会暴露技术细节的创作产品；  
> 底层负责参数，界面负责创作，供应商原始参数、接口、数据库和运行时细节不得向普通用户界面泄漏；供应商 / 模型身份与能力支持应保持透明；  
> 最后停止新增功能，用完整测试、正式环境、异常恢复、真实模型和发布包证明稳定。  
> DeepSeek + Agnes 在第一版范围内持续授权使用，不因人为调用次数、任务长度或阶段数量主动停工；测试仍按影响范围分层，禁止无意义全量重复。  
> 执行默认持续到 `RELEASE_DONE`；只有真实外部硬阻塞才允许进入 `GOAL_BLOCKED`。  
> 稳定以后发布第一版；自由画布和三维导演台从下一版开始。
