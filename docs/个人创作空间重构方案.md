# DramaForge 个人创作空间重构方案

**状态：IMPLEMENTED / 历史决策记录**

> 当前产品方向与阶段路线以 [`../DramaForge总开发文档.md`](../DramaForge总开发文档.md)
> 和 [`current/04-执行路线图.md`](current/04-执行路线图.md) 为准。本文保留个人 Workspace
> 重构的决策背景与实施边界。

## 决策摘要

DramaForge 从团队协作导向收敛为个人创作工具。

- 保留注册、登录和多账号隔离。
- 一个登录账号可以创建和管理多个私有创作空间。
- 一个创作空间只能属于一个账号，不能共享、转让、邀请成员或配置角色。
- 删除组织、成员、角色及其团队协作语义，不以隐藏 UI 的方式保留。
- 当前只有可丢弃的开发/测试数据，因此重置开发数据库并直接采用新模型，不做旧数据兼容迁移。
- 本地开发默认采用 Docker Compose，不要求人工维护 PostgreSQL、Redis、MinIO 或 Python 虚拟环境。

## 产品模型

用户看到的层级如下：

```text
账号
  -> 创作空间
    -> 项目
      -> 剧本、角色、素材、分镜、生成任务、导出结果
```

示例：账号 `alice@example.com` 可以拥有以下私有空间：

```text
我的短剧实验室
客户 A 定制项目
抖音账号一号
抖音账号二号
```

切换空间后，只显示该空间自己的项目、素材、预算、生成记录和 API 凭证。空间之间不能相互读取数据，即使它们属于同一个账号。

注册完成后，系统自动创建一个默认空间，例如“我的创作空间”。用户可以新增、重命名、切换和删除自己尚未承载项目的空间。

## 数据与权限模型

新的直接归属关系为：

```text
User
  -> Workspace(owner_user_id)
    -> Project(workspace_id)
```

需要移除的团队数据和概念：

- `Organization` 与 `organization_id`
- `OrganizationMember`
- `ProjectMember`
- `MemberRole`，包括 `owner`、`admin`、`editor`、`reviewer`、`viewer`
- 成员邀请、成员列表、角色校验和团队级组织 API

所有原本依赖角色的写入、审核、导出和凭证操作，统一校验为：当前登录用户是否是该空间的 `owner_user_id`。产品中不展示 owner 角色，因为空间天然只属于该用户。

PostgreSQL RLS 继续保留，但边界调整为：

- 用户只能读取和修改 `owner_user_id = current_user_id` 的空间。
- 项目只能在当前用户拥有的空间中访问。
- 所有直接或间接归属项目的业务表继续按项目上下文隔离。
- Worker 从数据库中的项目和空间重建用户上下文，不信任队列消息声明的归属。

## 数据保存方式

业务数据分为两类：

| 类型 | 存储位置 | 内容 |
| --- | --- | --- |
| 结构化业务数据 | PostgreSQL | 账号、空间、项目、剧本、分镜、任务、事件、审批、成本、预算、素材元数据、BYOK 密文 |
| 二进制媒体文件 | MinIO | 上传素材、生成图片、视频、音频、导出包 |

Redis 仅用于队列、任务调度和临时运行状态，不作为长期业务数据的唯一来源。

Docker Compose 使用命名卷保存长期数据：

```text
postgres_data -> PostgreSQL 数据目录
minio_data    -> MinIO 媒体文件目录
```

日常停止或重启容器不会清除数据：

```powershell
docker compose down
```

以下命令会删除开发数据卷，包含账号、空间、项目和媒体文件：

```powershell
docker compose down -v
```

在本次模型重构开始时可以使用带 `-v` 的命令重置测试数据；开始保存真实创作资料后禁止使用该命令，并应执行 PostgreSQL 与 MinIO 的独立备份。

## Docker 开发与部署

Docker Compose 是推荐的本地运行方式，容器包含：

```text
PostgreSQL
Redis
MinIO
API
默认 Worker
重任务 Worker
```

API 和 Worker 在 Docker 内网通过服务名连接：

```text
API/Worker -> postgres:5432
API/Worker -> redis:6379
API/Worker -> minio:9000
```

服务间通信完全在 Docker 内网完成；宿主机只通过已发布端口访问 API、PostgreSQL、Redis 和 MinIO。日常开发不需要安装或维护额外的 Linux 子系统、系统级 PostgreSQL 或独立 Python 虚拟环境。

Compose 启动流程应调整为先执行：

```text
alembic upgrade head
```

再启动 API 和 Worker，确保从空数据库启动时自动建立最新结构。

Docker Desktop 的数据盘应配置到 D 盘，例如 `D:\DockerDesktop`。镜像、容器、构建缓存以及命名卷数据将随 Docker 的磁盘镜像存放到该位置，项目 Compose 文件无需为此修改。

## 磁盘规划

默认 Compose 不启用 GPU 或 ComfyUI，也不会下载大模型。建议空间如下：

| 使用阶段 | 建议可用磁盘 |
| --- | --- |
| 接口、UI 和假数据验证 | 10 GB |
| 持续开发并保留少量生成素材 | 20 GB |
| 保留大量图片、视频、多版本和导出包 | 50 GB 起，建议按素材量扩容 |

MinIO 中的图片、视频、音频和导出结果是主要增长来源。不要启用 `docker-compose.gpu.yml`，除非已经为模型和 GPU 运行准备了额外数十 GB 以上的空间。

## 重构范围

实施时需要同步更新以下层面：

- Alembic 迁移、SQLAlchemy 模型和 PostgreSQL RLS 策略。
- FastAPI 路由、请求/响应 schema 与 OpenAPI 类型。
- 项目创建、快速创作、生成、导出、BYOK 解析和 Worker 的空间归属校验。
- 前端空间选择、空间管理、项目创建流程和所有产品文案。
- 单元测试、PostgreSQL 集成测试、端到端测试及测试夹具。
- 当前依赖组织、成员、角色的冻结数据文档、ADR 和运行文档。

不在本次范围内：共享空间、多人协作、成员邀请、项目协作、角色权限、空间转让、跨空间资产共享与组织兼容 API。
