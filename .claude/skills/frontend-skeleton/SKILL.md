# Frontend Skeleton（前端骨架）

骨架是 AI 写前端代码的前提。骨架不是"某个页面好不好看"，而是让任何一次 AI 生成都落在同一套结构、同一套视觉语言、同一套复用规则里的约束集合。项目越大越需要统一规范和标准；初期不建骨架，后期必然出现样式漂移、组件重复和越界改动。

## 何时使用

- 新项目/新模块在让 AI 写第一个页面前。
- 现有前端出现：同一种按钮写出多种实现、字号间距随手写、同一 UI 结构到处复制、跨模块互相引用内部文件。
- 被要求"重构前端骨架 / 统一 UI 规范 / 收敛组件库"时。

## 核心规则

1. **先定骨架，再写页面。** 骨架未定的部分不允许 AI 自由发挥；宁可先留空，也不要让 AI 随手发明一套。
2. **框架管结构，组件库管界面。** 技术方案（路由、目录、构建、部署）和 UI 组件库（按钮、输入、弹窗、表格）是两件事，分别选定、分别约束。
3. **不绕开框架与组件库。** 优先复用选定组件库；组件库不够用时，基于它封装项目自己的业务组件；禁止到处手写重复组件。
4. **出现超过两次就抽象。** 同类 UI 结构出现超过两次必须提取为可复用组件，不允许复制粘贴重复实现。
5. **样式只从 Token 取。** 颜色、字号、行高、间距、圆角、阴影、时长一律走设计 Token，不允许硬编码。
6. **文本不硬编码。** 用户可见文案、按钮、标题、提示与错误信息走统一文案层，为多语言与长度差异预留。
7. **主题可控。** 主色与主题扩展方式集中定义，不允许主题色散落在各页面。
8. **落地成实施计划。** 口头聊完就开写等于没有骨架；骨架结论必须写进实施计划并被后续任务引用。

## 六个工作面（逐项落定）

### 1. 整体设计风格

用一句话定义统一视觉语言（简洁 / 商务 / 科技 / 年轻 / 工具化 / 内容型），并把风格落到可执行细节：颜色、字体、字号层级、行高间距、圆角、卡片样式、按钮形态、布局与信息密度。

- 定不下来就收集 3–5 个参考链接或参考截图，让 AI 分析其视觉风格、布局方式、组件特点与适配性。
- 参考用于**确定方向**，不允许直接复制成熟产品的视觉节奏、留白方式和组件组织方式。
- 产物：风格词 + 设计 Token 的具体取值，而不是形容词清单。

### 2. 技术方案与 UI 组件库

- 技术方案解决"怎么组织、怎么运行"：React / Vue / Next.js / Taro / Uni-app 等 + 路由、目录、启动、构建、部署约定。
- UI 组件库解决"界面元素怎么统一"：Ant Design / Element Plus / Naive UI / MUI / Vant / ShadCN UI 等。
- 约束写法：必须遵守框架官方规范；优先复用选定组件库；不允许手写重复组件；不允许绕开框架自建平行体系。
- 检查点：组件库是否真的被业务代码引用（只装了但没人用 = 等于没选）。

### 3. 目录与模块边界

- 目录回答：页面、组件、请求、工具、样式、类型分别放哪里，新文件该落在哪一层。
- 模块边界回答：登录、用户、订单、内容等业务区域如何切分，避免一个功能散落全仓。
- 硬约束：业务模块之间不得直接引用对方内部实现文件；共享内容上提到共享层或公共包。
- 检查点：能否只看路径就判断一个文件的归属与职责；是否存在跨模块的深层相对路径引用。

### 4. 组件复用规则

- 优先组件库 → 组件库不足时基于组件库封装业务组件 → 跨模块通用的原语上提到共享层。
- 阈值：UI 相似度高且出现超过两次 **必须** 抽象为组件，禁止复制粘贴。
- 每个共享原语要有唯一实现位置；发现两处实现同一原语时，收敛为一处而不是新增一处。
- 检查点：设计系统原语是否被业务代码实际采用（存在但零引用的原语等于死代码）。

### 5. 样式系统准备

- **设计 Token**：颜色、字号、行高、间距、圆角、阴影、层级、时长。必须集中定义并作为唯一来源。
- **多语言**：不硬编码文案；中文两个字能放下，英文可能是一整句，后切语言会出现按钮错位、标题换行、布局错位。
- **主题规则**：默认主色 + 主题扩展方式集中定义，换主色只改一处。
- 硬约束：不硬编码颜色、字号、间距、圆角、阴影；不硬编码用户可见文案。
- 检查点：全量搜索硬编码色值/字号是否只出现在 Token 文件；语义状态（成功/警告/危险）是否都有 Token。

### 6. 实施计划

必须写清并纳入任务：

- 整体设计风格；前端技术方案；UI 组件库；目录结构；模块边界；
- 哪些组件先封装；设计 Token 如何定义；多语言与主题如何预留；
- 第一阶段只做哪些内容；验收标准（可执行、可观察）。

## 从零建立骨架的顺序

1. 定义风格词与 Token 取值，落成 Token 文件。
2. 选定框架与 UI 组件库，写进项目规则与实施计划。
3. 建目录骨架与模块边界，写清"新文件放哪"。
4. 落共享原语（按钮、输入、卡片、徽标、页头、标签页等）与复用阈值规则。
5. 落样式系统：Token、文案层、主题规则。
6. 写实施计划与验收标准。
7. **让 AI 按骨架写第一个页面，并用它反向校验骨架是否可执行。**

## 现有项目重构顺序（骨架已部分存在时）

1. **盘点既有骨架**：Token、组件库、目录、原语、文案层是否已存在，位置在哪。
2. **对照六个工作面找缺口**，把缺口分成"缺失"与"存在但没被采用"两类——后者通常收益最高、风险最低。
3. **先统一到已存在的正确实现**，不要新建第二套体系。
4. **收敛硬编码**：色值、字号、间距回填 Token；文案回填文案层。
5. **收敛越界引用**：跨模块引用改为经共享层或公开入口。
6. **固化约束**：写进项目规则与实施计划，必要时加自动化检查，防止回退。
7. **验证**：类型检查、静态检查、单测、构建与关键流程回归；行为与文案不因重构改变。

## 验收清单

- [ ] 设计风格有明确取值，且全部可在 Token 文件中找到。
- [ ] 业务代码使用选定的组件库/共享原语，而不是平行重写。
- [ ] 共享原语唯一实现且被实际引用，无零引用死代码。
- [ ] 目录与模块边界清晰，无跨模块内部深层引用。
- [ ] 同类 UI 结构无重复实现（超过两次即已抽象）。
- [ ] 样式文件与组件中无非 Token 的硬编码色值/字号/间距。
- [ ] 用户可见文案经统一文案层。
- [ ] 骨架结论写在实施计划/项目规则中，并有验收标准。
- [ ] 重构后类型检查、静态检查、单测、构建、关键流程全部通过，用户可见行为不变。

## 反模式

- 先写页面，再"以后统一"。
- 装了组件库但业务代码全手写。
- 共享原语目录存在但无人引用（本技能要优先消除的情况）。
- 业务模块直接引用另一个业务模块的内部文件与样式。
- 在同一份样式表里既定义 Token 又硬编码色值。
- 口头约定代替文档，改一个页面的风格要靠翻旧代码猜。
